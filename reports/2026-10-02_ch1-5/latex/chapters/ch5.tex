\section{Analysis and Design}

\subsection{Analysis}

\subsubsection{Business process modelling}

The three processes identified in Section 4.1.2 are modelled below. Diagram sources are given in a text notation for reproduction in the project's modelling tool.

Exploration process. The process begins with authentication and ends either in occupation completion and rating or in the user selecting a different occupation. The decision points are the optional orientation, the response type within a task, and the unlock evaluation on level completion.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.9\textheight,keepaspectratio]{figures/fig1.png}
\caption{Exploration process}
\end{figure}

Content lifecycle process. This process governs occupational accuracy and is the operational expression of BR-05. Domain experts author and review content in the system; the content administrator presents, publishes, and maintains it.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.9\textheight,keepaspectratio]{figures/fig2.png}
\caption{Content lifecycle process}
\end{figure}

Evaluation process. This process is internal to the project and supports RP-1 and RP-2. Experts construct reference items stratified by difficulty; generation output and assessor output are compared against them; agreement is computed with chance correction and reported per stratum, together with test--retest consistency.

\subsubsection{Use case modelling}

Four actors correspond to the user groups in Section 4.2.1. Two external systems also participate, though they are not drawn in the diagram: the model provider, which performs generation and assessment, and the occupational data source, which supplies reference data. Use cases in the diagram are named; the descriptions below also give each an identifier by actor (UC-E for the explorer, UC-D for the domain expert, UC-C for the content administrator, and UC-S for the system administrator), and the traceability matrix refers to them by name. A use case joined to another by an include relation is always performed as part of it; one joined by an extend relation is performed only under the condition stated in the flow of the use case it extends.

\centering
\includegraphics[width=\textwidth,height=0.9\textheight,keepaspectratio]{figures/jobquest_ucdiagram-1.png}

Use case descriptions follow, grouped by actor. Use cases associated directly with an actor, and those involving the AI model, are described in full; small included or extending use cases are described in abbreviated form. Author scenario and Review scenario are the use cases on which RP-1 depends, and Perform scenario, through Assess answer, is the one on which RP-2 depends.

Explorer use cases.

\begin{usecase}{UC-E01}{Register account}
\ucrow{Dependencies}{%
  \ucitem{FR-01 \textit{Register, sign in, and recover the account}}
  \ucitem{NFR-05 \textit{Minimal, encrypted, deletable personal data}}
  \ucitem{NFR-17 \textit{Passwords hashed, traffic encrypted}}
  \ucitem{DR-16 \textit{User accounts, roles, assignments, and activity log}}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{a visitor without an account creates one to start exploring}.}
\ucrow{Precondition}{\textit{The visitor has opened JobQuest and is not signed in.}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{Actor \textit{visitor opens JobQuest}.}
\ucstep{2}{The system \textit{checks access and shows the sign-in screen}.}
\ucstep{3}{Actor \textit{visitor chooses to register and provides the account details}.}
\ucstep{4}{The system \textit{creates the account}.}
\ucstep{5}{The system \textit{starts a session}.}
\ucstep{6}{The system \textit{opens the orientation quiz}.}
\ucrow{Postcondition}{\textit{The account exists and the explorer is signed in.}}
\ucsteps{Exceptions}
\ucstep{2}{If \textit{the visitor is already signed in}, the session continues, then this use case \textit{is cancelled}.}
\ucstep{3}{If \textit{the visitor already has an account}, the visitor \textit{signs in instead}, then this use case \textit{is cancelled}.}
\ucrow{Comments}{\textit{Only minimal personal data is collected and stored encrypted (NFR-05). Passwords are stored as salted hashes (NFR-17).}}
\end{usecase}

\ucsteps{Ordinary Sequence}

\begin{usecase}{UC-E03}{Complete orientation quiz}
\ucrow{Dependencies}{%
  \ucitem{FR-03 \textit{Optional, retakable RIASEC orientation quiz}}
  \ucitem{NFR-05 \textit{Only de-identified data sent to AI providers}}
  \ucitem{DR-12 \textit{Quiz answers, RIASEC profile, and AI portrait}}
  \ucitem{Includes UC-E04 \textit{Build user portrait}}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{an explorer takes the optional RIASEC quiz to receive occupation suggestions}.}
\ucrow{Precondition}{\textit{The explorer is signed in.}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{Actor \textit{explorer opens the orientation quiz and chooses to take it now}.}
\ucstep{2}{The system \textit{shows the quiz questions}.}
\ucstep{3}{Actor \textit{explorer answers every question and submits the answers}.}
\ucstep{4}{The system \textit{calculates the RIASEC profile}.}
\ucstep{5}{The system \textit{matches the profile with the O*NET interest code of each occupation and picks the five closest occupations}.}
\ucstep{6}{The system \textit{builds the user portrait} (UC-E04).}
\ucstep{7}{The system \textit{saves the profile, replacing any earlier result}.}
\ucstep{8}{Actor \textit{explorer views the description, the social index, and the five suggested occupations}.}
\ucstep{9}{Actor \textit{explorer picks an occupation}, and the system \textit{opens it}.}
\ucrow{Postcondition}{\textit{The RIASEC profile, the portrait, and the suggestions are stored.}}
\ucsteps{Exceptions}
\ucstep{1}{If \textit{the explorer skips the quiz}, the system \textit{opens the Galaxy Map}, then this use case \textit{is cancelled}.}
\ucstep{3}{If \textit{some answers are missing}, the system \textit{highlights them}, then step 3 \textit{repeats}.}
\ucstep{9}{If \textit{the explorer chooses to browse all occupations}, the system \textit{opens the Galaxy Map}.}
\ucrow{Comments}{\textit{The quiz follows Holland's RIASEC model \cite{r41}. The suggestions are computed without AI. The number of suggestions, five, is project-defined (FR-03).}}
\end{usecase}

\begin{usecase}{UC-E04}{Build user portrait}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{a RIASEC profile has to be turned into a portrait}.}
\ucrow{Precondition}{\textit{The RIASEC profile has been calculated (UC-E03, step 4).}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{The system \textit{takes the Social score as the social index}.}
\ucstep{2}{The system \textit{sends the de-identified profile to the AI model}.}
\ucstep{3}{The AI model \textit{writes the user description}.}
\ucstep{4}{The system \textit{checks the description}. If \textit{the check fails}, step 3 \textit{repeats}.}
\ucstep{5}{The system \textit{labels the portrait as self-reported and not validated}.}
\ucrow{Postcondition}{\textit{The portrait is stored with the profile.}}
\end{usecase}

\begin{usecase}{UC-E11}{Perform scenario}
\ucrow{Dependencies}{%
  \ucitem{FR-09 \textit{Show role, team, and context before each scenario}}
  \ucitem{FR-10, FR-11 \textit{Answer forms and anchored scoring}}
  \ucitem{FR-13, FR-14, FR-15 \textit{Hints, feedback, and recorded competencies}}
  \ucitem{NFR-03, NFR-04 \textit{Progress survives interruption and provider failure}}
  \ucitem{NFR-05, NFR-07 \textit{De-identified data; AI disclosure}}
  \ucitem{DR-06, DR-07 \textit{User progress; assessment records}}
  \ucitem{Includes UC-E12, UC-E13; extended by UC-E14, UC-E15, UC-E16, UC-E17, UC-E18; extends UC-E08}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{an explorer plays a published scenario of a level they are enrolled in}.}
\ucrow{Precondition}{\textit{The explorer is signed in, is enrolled in the level, and has chosen a main quest (UC-E08).}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{The system \textit{loads the scenario at the saved position and shows the role, team, and goal} (UC-E12).}
\ucstep{2}{Actor \textit{explorer reads the scenario context}.}
\ucstep{3}{The system \textit{opens the activity and shows the NPC line}.}
\ucstep{4}{Actor \textit{explorer submits an answer}.}
\ucstep{5}{The system \textit{assesses the answer} (UC-E13).}
\ucstep{6}{The system \textit{shows the NPC closing line, records the competencies, and saves progress}.}
\ucstep{7}{Steps 3--6 \textit{repeat for each remaining activity}.}
\ucstep{8}{The system \textit{counts the +2 and $-1$ marks and picks the ending that matches the score}.}
\ucstep{9}{The AI model \textit{writes the strengths, the improvements, and one tip for next time}.}
\ucstep{10}{The system \textit{updates the progress bars, saves the play history and badges, and checks the credit for the next level} (UC-E17).}
\ucstep{11}{Actor \textit{explorer views the ending, the feedback, and the guidance, then returns to the Island Map}.}
\ucrow{Postcondition}{\textit{The evidence, progress, and play history are stored, and the explorer has received the ending, feedback, and guidance.}}
\ucsteps{Exceptions}
\ucstep{1}{If \textit{the scenario is not available}, the system \textit{returns the explorer to the Galaxy Map}, then this use case \textit{is cancelled}.}
\ucstep{3}{If \textit{a random event is triggered}, the system \textit{shows it}, actor \textit{explorer responds}, and the AI model \textit{grades the response as bonus soft-skill evidence}. The sequence \textit{continues at step 4}.}
\ucstep{4}{Actor \textit{explorer may open a hint} (UC-E15). The +2 mark of the activity \textit{is then lowered to 0}.}
\ucstep{4}{If \textit{the explorer leaves the scenario}, the system \textit{saves progress and returns to the Island Map}. The scenario \textit{later resumes at the saved position}.}
\ucstep{5}{If \textit{a free-text answer needs a follow-up and the limit has not been reached}, UC-E14 \textit{Answer follow-up question} runs.}
\ucstep{10}{If \textit{the credit is not enough}, the system \textit{suggests tasks to practise}.}
\ucstep{11}{If \textit{the occupation is completed}, actor \textit{explorer may rate it} (UC-E18) \textit{or open the profile}.}
\ucrow{Comments}{\textit{AI-written follow-ups and feedback must pass the output check, otherwise the expert's default is shown (FR-12, FR-14). Credit is capped per skill per scenario, so replaying never inflates it (FR-15). Random-event answers add bonus soft-skill evidence only and never lower the main score (FR-15, FR-22).}}
\end{usecase}

\begin{usecase}{UC-E13}{Assess answer}
\ucrow{Dependencies}{%
  \ucitem{FR-10 \textit{Choice, ordering, prioritising, and free-text answers}}
  \ucitem{FR-11 \textit{Anchored scoring backed by quotations}}
  \ucitem{FR-13, FR-15 \textit{Hint penalty; capped competencies}}
  \ucitem{NFR-02, NFR-04, NFR-05, NFR-14, NFR-17}
  \ucitem{DR-07 \textit{Assessment records}}
  \ucitem{Included by UC-E11 and UC-E14}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{an answer submitted by the explorer has to be scored}.}
\ucrow{Precondition}{\textit{The explorer has submitted an answer to an activity.}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{The system \textit{checks the answer type}.}
\ucstep{2}{The system \textit{de-identifies the free-text answer}.}
\ucstep{3}{The system \textit{sends the answer to the AI model as separated data, together with the rubric anchors}.}
\ucstep{4}{The AI model \textit{grades the answer against the anchors, quoting the explorer's words}.}
\ucstep{5}{The system \textit{checks that every quotation appears verbatim in the answer and that the score is a rubric anchor}.}
\ucstep{6}{The system \textit{keeps the evidence with the exact quotations}.}
\ucstep{7}{The system \textit{records the competencies, capped per skill per scenario}.}
\ucrow{Postcondition}{\textit{The evidence is stored with its quotation.}}
\ucsteps{Exceptions}
\ucstep{1}{If \textit{the answer is a choice, ordering, or prioritising answer}, the system \textit{scores it with the expert's scores}, then the sequence \textit{continues at step 7}.}
\ucstep{4}{If \textit{the AI provider fails}, the system \textit{keeps the progress and notifies the explorer within 10\,s} (NFR-04).}
\ucstep{5}{If \textit{a quotation is not found or the score is outside the anchors}, the system \textit{rejects the result}.}
\ucstep{7}{If \textit{a hint was used in this activity}, the system \textit{lowers +2 to 0}.}
\ucrow{Comments}{\textit{Free-text assessment finishes within 8\,s at the 95th percentile (NFR-02). Instructions written inside an answer are ignored (NFR-17). Agreement with experts is checked under NFR-14.}}
\end{usecase}

\begin{usecase}{UC-E14}{Answer follow-up question}
\ucrow{Dependencies}{%
  \ucitem{FR-12 \textit{AI-generated follow-up questions}}
  \ucitem{NFR-01 \textit{Follow-up generation time}}
  \ucitem{NFR-15 \textit{AI content stays within expert-set limits}}
  \ucitem{Extends UC-E11; includes UC-E13}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{the AI model probes a free-text answer further}.}
\ucrow{Precondition}{\textit{A free-text answer has been assessed, a follow-up is needed, and the follow-up limit of the activity has not been reached.}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{The AI model \textit{generates a follow-up question within the expert's follow-up goal}.}
\ucstep{2}{The system \textit{runs the output check}.}
\ucstep{3}{The system \textit{shows the follow-up question}.}
\ucstep{4}{Actor \textit{explorer answers the follow-up question}.}
\ucstep{5}{The system \textit{assesses the answer} (UC-E13).}
\ucstep{6}{Steps 1--5 \textit{repeat while a follow-up is needed and the limit has not been reached}.}
\ucrow{Postcondition}{\textit{The follow-up answers are stored with their evidence.}}
\ucsteps{Exceptions}
\ucstep{1}{If \textit{generation takes longer than 2\,s}, the system \textit{shows progress} (NFR-01).}
\ucstep{2}{If \textit{the output check fails}, the system \textit{shows the expert's default follow-up instead}.}
\ucrow{Comments}{\textit{Follow-ups are generated within 5\,s at the 95th percentile (NFR-01), and only for free-text answers.}}
\end{usecase}

\begin{usecase}{UC-E18}{Rate occupation}
\ucrow{Dependencies}{%
  \ucitem{FR-19 \textit{Collect occupation ratings and feedback}}
  \ucitem{NFR-06 \textit{Suppress aggregates below a minimum population}}
  \ucitem{DR-08 \textit{Five-attribute occupation ratings}}
  \ucitem{Extends UC-E11}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{an explorer rates an occupation after completing it}.}
\ucrow{Precondition}{\textit{The explorer has completed every level of the occupation.}}

\ucstep{1}{Actor \textit{explorer opens the occupation rating}.}
\ucstep{2}{The system \textit{confirms that the occupation is completed}.}
\ucstep{3}{Actor \textit{explorer writes feedback and rates the occupation}.}
\ucstep{4}{The system \textit{saves the rating and updates the average}.}
\ucstep{5}{The system \textit{shows the ratings of other explorers}.}
\ucstep{6}{Actor \textit{explorer views the occupation profile}.}

\begin{usecase}{UC-E20}{View personal record}
\ucrow{Dependencies}{%
  \ucitem{FR-18 \textit{Private record of attempts, points, and awards}}
  \ucitem{DR-06 \textit{User progress}}}
\ucrow{Description}{The system shall behave as described in the following use case when \textit{an explorer reviews what they have attempted and demonstrated}.}
\ucrow{Precondition}{\textit{The explorer is signed in.}}
\ucsteps{Ordinary Sequence}
\ucstep{1}{Actor \textit{explorer opens the personal record}.}
\ucstep{2}{The system \textit{rebuilds the record from the session history: attempts, expertise points, soft-skill points, and awards}.}

\subsection{Technology Solution}

The technology stack of JobQuest is chosen from what the requirements ask of each part of the system. Three properties of the requirements drive most choices: a written answer waits several seconds on external models that can fail (NFR-01, NFR-02, NFR-04); scores unlock levels and occupations, so the server must score authoritatively by the same rules the browser uses for immediate feedback (BR-02, BR-11, FR-15); and personal data must be processed and stored in Vietnam (DC-03). Sections 5.2.1 and 5.2.2 state, for each component of the frontend and backend, what it must do, with the requirements behind it, and the decision taken: the technology and the features of it that meet those requirements. The selected stack is summarised at the end of Section 5.2.2, and Section 5.2.3 covers the AI design. Versions are those resolved in the workspace lockfile at the time of writing.

\subsubsection{Frontend}

The frontend serves two populations. Explorers, in twenty-one of the fifty-six use cases of Section 5.1.2, play on their own phones over weak connections (NFR-13), may use assistive technology (NFR-19), read the interface in Vietnamese (NFR-08; only Vietnamese is supported in this phase), and wait seconds while a model assesses a written answer (NFR-01, NFR-02). Staff, in the other thirty-five, work at desktops in forms, review queues, and tables (FR-21 to FR-44).

Application framework. The frontend must render a game interface with many interacting states --- the occupation map, conversations with characters, the four response forms of FR-10, hints, follow-up questions, and results (FR-05, FR-07, FR-10 to FR-14). It must show provisional feedback on closed formats at once, by the same rules the server applies (FR-15, BR-11), stay responsive while a model works (NFR-01, NFR-02), and load quickly on a mid-range phone without installation (NFR-13, DC-05). Every route except the landing page requires sign-in (FR-01), so no screen needs search indexing.

\textbf{Decision: React 19 with Vite 8, as a client-rendered single-page application.} React's component model fits an interface of many independent, stateful parts, and it is the most used web framework, by 44.7\% of developers\cite{r136}, so libraries for drag-and-drop ordering, 3D rendering, and accessibility are mature. Running in the browser lets the shared rules package, \textit{game-core}, compute provisional scores without a round trip. React 19's optimistic-update hook shows ``saved, assessing'' the moment an answer is sent\cite{r137}. Vite's production build splits code into chunks loaded on demand\cite{r138}: the prototype's entry was about 195 KB compressed in the build of 18 September 2026, and a budget of 200 KB for the first interactive screen, about one second under the Lighthouse mobile profile\cite{r139}, is checked in continuous integration. Server-side rendering is not used: with every screen behind sign-in it brings no indexing benefit, and it would add a server that renders personal data, whereas static files hold none and can be cached on a content delivery network without affecting DC-03.

Occupation map. The map must convey the progression metaphor of Section 4.2.1 (FR-05, FR-07), remain operable with a keyboard and a screen reader (NFR-19), and not exclude low-end devices (NFR-13).

\textbf{Decision: three.js 0.186 through @react-three/fiber 9.7, with an SVG view drawn from the same data.} @react-three/fiber writes the 3D scene as React components that share state with the rest of the interface\cite{r140}. Because a canvas exposes nothing to a screen reader and a 3D scene costs GPU work every frame\cite{r141}, an SVG view, in which each planet is a focusable, named element\cite{r142}, is the accessible equivalent. It can be chosen at any time and is used automatically when WebGL is missing or lost, when reduced motion or data saving is requested, or on low-memory devices. The 3D libraries, about 310 KB compressed, load only when the 3D view opens.

Styling. Styles must add little to the download (NFR-13) and let each occupation carry its own theme without code changes (NFR-10).

\textbf{Decision: Tailwind CSS 4.3.} It generates CSS only for the classes used and has no runtime\cite{r143}; occupation themes are design tokens held as CSS variables and supplied by content data.

Client state. Client state must apply \textit{game-core}'s reducer directly (FR-10, FR-15) and keep unsent turns through a lost connection (NFR-03).

\textbf{Decision: zustand 5.0.} A store wraps the reducer, so one dispatch updates both screen and rules state; its persistence middleware keeps unsent turns in browser storage, resent with an idempotency key on reconnection\cite{r144}. It needs no provider tree and adds little to the bundle.

Routing. Routing must keep the 3D map and all staff code out of the explorer's first download (NFR-13), separate explorer and staff areas by role (FR-41), and resume a run on any device (NFR-03).

\textbf{Decision: React Router 7.18.} Routes load on demand, nested layouts separate the areas by role, and route loaders fetch the state of an interrupted run from the server\cite{r145}.

Result delivery. Assessment results must reach the explorer as soon as they are ready (NFR-02, FR-14) over connections that drop (NFR-13). Only the server needs to push; the client submits answers by ordinary requests.

\textbf{Decision: server-sent events.} The browser's built-in \textit{EventSource} receives pushed events over plain HTTP, through any proxy, and reconnects by itself\cite{r146}; a bidirectional WebSocket channel is not needed.

Staff application. Staff work in review queues, lists, and statistics (FR-21 to FR-44), in dialogs, comboboxes, and grids, where hand-built interfaces most often fail accessibility (NFR-19).

\textbf{Decision: the same stack, plus TanStack Query and React Aria.} TanStack Query caches and refreshes server data\cite{r147}; React Aria supplies accessible interaction primitives\cite{r148}. The staff application is a separate bundle on the same origin and sign-in screen.

Localisation. Only Vietnamese is supported in this phase, while NFR-08 still names Vietnamese and English and is to be aligned. Interface strings must be complete in every supported language, and adding English later must not require changes to the screens.

\textbf{Decision: a typed message table with the standard \textit{Intl} API.} An unknown key fails compilation and a test fails a missing translation; plurals, dates, and numbers are formatted by \textit{Intl}\cite{r149}; content fields carry a locale, so a second language is added as data. Generated text is inserted as text, which React escapes, so model output cannot inject markup (NFR-17)\cite{r150}.

\subsubsection{Backend}

The backend carries five kinds of work: short requests for navigation, records, and staff edits; durable recording of every turn as it happens (NFR-03); assessment and follow-up generation, which wait seconds on external models and occasionally fail (NFR-01, NFR-02, NFR-04); authoritative scoring (BR-02, BR-11); and a governed content lifecycle with logged transitions (NFR-16).

Application framework. Most backend time is spent waiting --- on models, on the database, on open result streams --- and at Stage 4 about five thousand explorers are connected at once (Section 5.3.1). The framework must also give the modular structure of Section 5.3.1 clear module boundaries, check occupation-scoped roles on every request (FR-40, FR-41), integrate a job queue and server-sent events, and score by the same rules as the browser (FR-15, BR-11).

\textbf{Decision: NestJS 11.1 on Node.js, in TypeScript.} Node.js serves I/O on an event loop, so a waiting request or open stream costs memory rather than a thread. NestJS modules and dependency injection give each bounded context its own module; guards enforce occupation-scoped roles; interceptors write the activity log; and first-party integrations provide BullMQ queues and server-sent events\cite{r151}. Dependency injection also binds the model port to the provider adapter named in configuration (DC-02, NFR-12)\cite{r152}. The server imports the same \textit{game-core} package as the browser and recomputes every score from stored events. Models are called over HTTP and run nowhere in the process, so the request path needs no Python; the statistics for evaluating RP-1 and RP-2 run offline in Python scripts. Long computation, which would block an event loop, runs in worker processes.

Database. Much of the data is relational, with rules that span records: a reviewer is never the author (FR-25), one active scenario per task (FR-33), exactly one content administrator per occupation (FR-40), and the replay cap (BR-11). Publication and its log must be atomic, and published content immutable (NFR-16); scenario content is nested documents (NFR-10, NFR-15); statistics are shown only above a population threshold (NFR-06, FR-19, FR-39); and the store must be hostable in Vietnam (DC-03).

\textbf{Decision: PostgreSQL, accessed through Prisma ORM 7.10.} Foreign keys, check constraints, partial unique indexes, and transactions enforce the cross-record rules in the database itself --- ``one active scenario per task'' is a single partial index\cite{r153}. A transition and its log entry share one transaction, and a trigger refuses updates to published releases. Content is stored in \textit{jsonb} columns\cite{r154}, validated by \textit{game-core}'s schemas on write and read. Thresholded statistics are SQL grouping, window functions, and materialised views. PostgreSQL is open source, offered by every cloud provider, and the most used database, at 55.6\%\cite{r136}. Prisma generates a typed client from the schema and, from version 7, runs over the standard \textit{pg} driver\cite{r155}; partial indexes, checks, and triggers, which Prisma does not express, live in SQL migrations and are tested against the database.

Job queue and messaging. Model work must survive failures, be retried, and be listed for re-run when it fails (NFR-04, FR-43); it must respect each provider's rate limits and serve live play first --- narration and follow-ups for an explorer in a scenario before background scoring, and both before authoring work (NFR-01, NFR-11); results must reach the API replica holding the explorer's stream (NFR-02); and each session's model cost must be counted atomically (NFR-11).

\textbf{Decision: Redis with BullMQ 6.3.} BullMQ provides persisted jobs, retries with exponential backoff, job priorities, per-queue rate limiting, and a set of failed jobs for re-run\cite{r156}; Redis's publish--subscribe carries results to every API replica, and its atomic counters meter the session budget. Redis holds nothing that cannot be rebuilt from PostgreSQL, and a scheduled reconciliation re-queues any stored answer without a result, so losing Redis loses no answer.

Authentication. The platform must register, sign in, recover, and delete accounts (FR-01, FR-02); hash passwords, protect sessions, and end idle ones (NFR-17); scope roles to occupations (FR-41); and keep identity data in Vietnam (DC-03).

\textbf{Decision: the platform's own module --- argon2id, JWT access and refresh tokens in httpOnly cookies, and optional Google sign-in.} Passwords are hashed with argon2id\cite{r157}; a fifteen-minute access token and a rotating refresh token with reuse detection\cite{r158} live in httpOnly, SameSite cookies that scripts cannot read; Google ID tokens are verified with google-auth-library. Accounts stay in the platform's database in Vietnam, which an external identity service would hold abroad, and occupation-scoped authorisation must live in the application whichever service is used. The module is completed against ASVS 5.0 level 2\cite{r159}: single-use, short-lived reset tokens; an inactivity limit; account status checked on every refresh and staff request; rate limiting of sign-in; and a second factor for staff.

Validation and code organisation. Every input and every model output must be checked against a schema (NFR-17, FR-11), and one copy of the rules and contracts must serve both applications, the API, and the worker (FR-15).

\textbf{Decision: Zod 4.6 schemas in an Nx 23.1 monorepo.} Zod schemas, shared by API, clients, and the rule checks, validate requests, content documents, and model output --- scores within rubric anchors, quotations verbatim. Nx keeps \textit{game-core} and the schemas in one repository, enforces module boundaries so staff code never enters the explorer's bundle (NFR-13), and builds and tests only what a change affects\cite{r160}.

Packaging and hosting. Personal data must be stored in Vietnam (DC-03, NFR-05) --- Decree 53/2022 further requires domestic online-service enterprises to store users' data in Vietnam, applicability to be confirmed (Section 4.1.4)\cite{r161,r162} --- and the platform must stay available (NFR-18) while growing from a university pilot to a national service.

\textbf{Decision: Docker containers, hosted in Vietnam.} One image runs as API or worker, with rolling deployment and health checks, and the platform depends only on portable services --- PostgreSQL, Redis, and S3-compatible storage --- so moving host is a change of configuration. The system of record runs on university infrastructure for the Stage 1 pilot and on a cloud provider in Vietnam from Stage 2\cite{r163}; an international region such as Singapore would make every account a cross-border transfer\cite{r99}. Only de-identified text leaves the country, through the model gateway. International providers adding capacity in Vietnam, such as the AWS Hanoi Local Zone, whose control plane remains in Singapore\cite{r164}, are reassessed with the legal office before Stage 2.

The five places where AI works. AI is used at five steps, three while content is authored and two during play. AI drafts, connects, scores, and filters; domain experts decide occupational content, scoring keys, and publication.

AI-1, interviewing the domain expert. A language model asks and probes to collect what a seed needs: incidents, what a good and a poor response look like, and the facts of the situation. Each expert is interviewed separately, and the merged content marks where experts agree and where they differ. The interview is constrained by a human-written topic guide based on the critical incident technique\cite{r26} and on development practice for situational judgment tests\cite{r27}; the model probes inside each topic only. A tracker lists the seed fields still missing, the expert is shown a summary and confirms it, and every turn is stored verbatim so that each seed field links to the turn it came from. That a language model can hold an interview to a guide is supported by 766 AI-led interviews in which 94.8\% to 99.8\% of questions were open-ended, 95.7\% to 99.6\% neutral, and 0.1\% to 0.4\% hallucinated\cite{r115}.

AI-2, drafting the game seed. The model helps the content administrator turn the experts' answers into a structured seed: context, characters, situations, canon events, and the scoring frame. Drafts are written from the expert's own words, the domain expert sets every scoring key and every rubric anchor, and a seed passes automatic structure checks and then the expert's approval before any player sees it. Experts own keys and rubrics because, when GPT-4 drafted 210 examination questions, specialists required revision of 15\% and judged 0.5\% false\cite{r116}. The seed follows evidence-centered design: what is measured, which behaviour is evidence for it, and which situation elicits that behaviour\cite{r20,r117}. This is the first of four checkpoints for generated content: structure is checked by machine and content is approved by the expert.

AI-3, helping the expert test before publishing. A volunteer expert with about seven hours cannot read every free-text answer. AI-3 runs AI-4 and AI-5 on test playthroughs, from experts, testers, and simulated answers, and ranks the cases that need the expert: cases where the three judges differ by more than one level, generated turns that broke a run-time rule, and a blind random sample of cases that were not flagged. The expert decides, and can refine a rubric anchor during review, so rubrics are versioned. The random sample is required because confidence signals from a language-model grader separate right from wrong grades only weakly, with an area under the curve of 0.57 to 0.64\cite{r118}, so flagged cases alone can hide errors; if n audited cases show no error, the error rate is at most about 3/n at 95\% confidence\cite{r119}. Simulated players find relative problems only: persona-prompted models answered with near-perfect, uniform accuracy, unlike 2,359 real students\cite{r120}, so real test plays are needed as well. The run-time checks of AI-4 are to be tested on scripted player turns in four classes (on-script, off-script, adversarial, and rubric-fishing), reporting the violation rate per class; this test set is not yet built. This is the second checkpoint, and the expert-scored test plays are also the validation data for the judge. In the present phase there are no experts or real players: the team stands in for both and the advisor checks a sample, so results show that the machinery works, not agreement with experts.

AI-4, narrating during play. The game engine, not the model, controls the order of canon events. Canon content is shown verbatim from the seed; a situation may have several approved canon variants chosen at random, and the log records which variant was served. The model writes only the connecting narration and the follow-up questions that fit the player's free-text answer. The whole seed is placed in the prompt, without retrieval or fine-tuning, and the rubric and scoring keys are not in the prompt. Run-time checks are rules, not another model call, so checking adds no waiting time: numbers and names must come from the seed or from the player's own text, and the engine counts follow-ups. A model from a different family reviews the logs afterwards. Holding authored structure outside free generation is the established approach in interactive narrative\cite{r121}, and when the source fits in the prompt, long-context prompting outperformed retrieval on average\cite{r122}. These are the third checkpoint (rules at run time) and the fourth (log review afterwards).

AI-5, scoring the playthrough. The scoring model is separate from the narrating model (DC-01). There is no reference answer: answers are free text, and the judge scores each rubric criterion by how far the answer meets the behaviour described for each level. Each judge is called once per situation, with at most three criteria in a call; the call runs in the background when the situation ends, and results appear on the summary screen. For each criterion the judge returns a verbatim quote from the player, then the rationale, then the level, and the quote must be a substring of what the player typed. A panel of three judges from three model families scores each situation and the median is the score; cases where judges differ by more than one level go to the expert through AI-3, and if one judge is unavailable the system waits for all three. One call for all criteria was not chosen because batching several rubric checks into one call trades accuracy for cost, with a large loss when the evidence is spread over a long trajectory\cite{r123}. A panel was chosen because a five-judge vote matched the best single judge, with a Pearson correlation with humans of 0.627 against 0.623\cite{r124}, so a panel reaches the best judge's level without knowing in advance which judge that is. The design does not claim that a panel is more accurate than a single judge.

Strength of the judge relative to the generator. The judge does not need to be stronger than the generator, because it scores text written by a person, not the generator's output. It does need enough capacity: small models aligned poorly with human raters (intraclass correlation below 0.20) and larger models moderately (0.41 to 0.57), against 0.45 between the two human raters\cite{r125}. It need not be a reasoning model: two reasoning models had lower validity than a smaller standard model in essay scoring\cite{r126}. Each judge family is therefore to be tested at two tiers, and the cheapest tier that is not clearly worse is chosen.

Reliability of a language-model judge. Published evidence supports a conditional answer, not reliability by default. On a standard essay dataset, mean quadratic weighted kappa was 0.313 for ChatGPT and 0.297 for Llama against 0.817 for the best supervised system\cite{r127}. Agreement nears human level with a strong model, an explicit rubric, and scored examples (Section 2.5)\cite{r101,r102,r103,r104,r105}; the present phase has the first two, and examples come later from expert rulings. Automated scorers handle fully correct and fully incorrect answers well and are much worse on partially correct ones, while human agreement stays constant\cite{r128}. A judge is only as good as its knowledge of the work: without a reference answer, judges agreed with experts only on questions they could answer themselves\cite{r129}, and judging ability tracks problem-solving ability\cite{r60}; since there is no reference answer here, the judge must know IT work and the rubric must carry domain knowledge. Judges favour their own generations\cite{r130}, hence a judge family other than the generator's. This evidence comes from another setting, English essays and short answers scored by earlier generations of models; none concerns Vietnamese or role-play. Reliability must therefore be measured on the project's own task (RP-2) against the criteria of Williamson, Xi and Breyer\cite{r71}: quadratic weighted kappa of at least 0.70, a standardised mean difference of at most 0.15, and agreement at most 0.10 below that between experts.

Framework for the judge. The offline test harness is Inspect AI, an open-source framework maintained by the UK AI Security Institute\cite{r131}. It provides repeated runs, several grader models in one run, a median reducer, and an ordinal Krippendorff's alpha; the project's rubric needs a custom scorer. In the product, the judge is the project's own TypeScript module with schema-validated output, and prompts and rubrics are kept in data files shared by both. These tools have no peer-reviewed papers; the cited science is in the method, rubric-based scoring with reasoning before the score\cite{r58} and panels of judges\cite{r74}.

AI-native character and provider failure. The definition adopted is that a system is AI-native when AI is constitutive of its core loop, so that removing the AI makes the central activity collapse or change fundamentally\cite{r132}, and when AI is part of design, operation, and maintenance, not an added component\cite{r133}. In JobQuest, AI works at all five steps: without it the system cannot fit the narration to a free-text answer and cannot score that answer, and there is no substitute path, neither keyword scoring nor a scripted replacement. When the model provider fails, generation and scoring, the core, stop; the session pauses, answers and progress are saved (NFR-04), and play resumes when the AI returns; pages that do not use AI, such as sign-in, the occupation map, and the profile, stay available; switching to another provider is still AI, not a fallback (DC-02). Several providers are used so that an outage at one provider does not take every AI function down at once.

The criteria are Vietnamese capability, knowledge of IT work, response time, price, schema-constrained output, and data terms. Staff application. The thirty-five staff use cases: the AI-1 interview through which a domain expert gives the knowledge a seed needs, review, test playthroughs, reliability, and blind rating for domain experts; seed drafting with AI-2, catalogue, presentation, publication, and statistics for content administrators; accounts, model configuration, monitoring, data requests, and feedback for system administrators. It shares the sign-in screen and origin with the explorer application (FR-41) but is a separate download. Prototype: absent.

Game core. A library with no framework, network, or storage dependency: the reducer folding run events into state, scoring of closed formats against expert keys, credit with the per-scenario cap, unlocking and adjacency offers, content schemas, and the rule checks on model output of Section 5.2.3 --- numbers and names in narration found in the seed or the player's text, the follow-up count, each judge's quotation found verbatim in the answer, levels within the scale. It runs unchanged in browser and server. Prototype: present; its free-text grader is a synchronous keyword matcher inside the reducer, which must become an asynchronous assessment entering the run as an event.

Identity and access. Accounts, sign-in and recovery, sessions, occupation-scoped roles, disabling, deletion, and the activity log (FR-01, FR-02, FR-40, FR-41); every module asks it whether an actor may act on an occupation. Prototype: registration, email and Google sign-in, rotating sessions, and deletion exist; reset, idle expiry, scoped roles, disabling, and the log do not, and the three prototype roles must become the four actors of Section 4.2.1.

Exploration. Everything outside the assessment itself: orientation, catalogue and profiles, enrolment, runs and their events, credit, unlocking, adjacency offers, side quests, ratings, records, and feedback (FR-03 to FR-09, FR-15 to FR-20). It validates turn events with \textit{game-core} and stores them; for each free-text answer it records a narration request, and when a situation ends a scoring request, each in the same transaction as the event that causes it. Prototype: present, but runs are submitted as one batch at the end.

Assessment. Turns answers into results, feedback, and guidance (FR-10 to FR-14). Closed formats are scored synchronously by \textit{game-core}; free text is scored in the background when its situation ends (AI-5), and the result, together with feedback written from the judges' output, is written back as events and shown on the summary screen in the three separate parts of FR-14. It also routes explorers' flags of wrong content to the occupation's domain experts. Prototype: closed formats scored by replaying the run; free text matched by keyword.

Content lifecycle. Occupations, knowledge, scenarios and drafts, generation history, review criteria, assignments and decisions, presentation, assets, and publication (FR-21 to FR-38). It is the only writer of content, implements the state machine SM-01, writes each transition with its log entry in one transaction, and publishes immutable, versioned releases. It uses AI orchestration for generation, validation, presentation, and missing assets; the scheduler for deadlines and annual revalidation; and the importer for O*NET and ESCO, whose interest codes also drive orientation matching (FR-03). A domain expert or content administrator can send a published scenario back for revalidation while it stays playable (FR-27). Prototype: versioned immutable documents, written only by a seed script.

AI orchestration. Runs every model use of the five AI components of Section 5.2.3 as a job: the expert interview (AI-1) and seed drafting (AI-2) at authoring time, with presentation design and missing assets (FR-35, FR-36); test playthroughs (AI-3); narration and follow-ups during play (AI-4, FR-12); and scoring by a panel of three judges (AI-5, FR-11), plus the portrait (FR-04). Per job it loads the pinned content version, removes identifying details from explorer text, checks the session budget, calls the model port, applies \textit{game-core}'s rule checks, and records model, prompt version, cost, and latency. There is no scripted substitute for a model's output: a job that cannot complete is retried or waits, and a session pauses until it can. It rechecks at job time that no judge shares the narrator's family or another judge's. Prototype: absent; queue and model-client libraries are declared but unused.

Model gateway. One adapter per provider and a registry recording each model's role --- text generation, assessment, image generation (FR-36) --- with its provider and family; configuration is refused when the narrator and a judge, or two judges, share either (FR-42, DC-01). It applies per-provider concurrency limits, timeouts, retries, and a circuit breaker. Whether adapters use providers' own clients or a unifying library is decided in Section 5.2.3. Prototype: absent.

Analytics. Everything shown only in aggregate: ratings and statistics above the population threshold, play-tests excluded (FR-19, FR-39, NFR-06, DR-11); coverage; agreement by difficulty stratum and the disagreement list (FR-28, NFR-14); and blind ratings (FR-29). Occupation ratings are re-aggregated in the transaction that stores each rating (FR-19); heavier statistics refresh periodically, later from a replica. It never returns an individual's record. Prototype: personal summaries only.

Operations. Telemetry of usage, cost, latency, and errors (DR-10); failed jobs and re-runs (FR-43); versioned settings, including the cost ceiling (DR-17); data-subject requests (FR-44); and feedback review (FR-20). Prototype: absent.

Notification, scheduler, and import. Notification sends email and in-app notices: reset links, review assignments, reminders, play-test invitations. The scheduler runs recurring jobs: review reminders and overdue notices (FR-34), annual revalidation (BR-15), retention, refreshing statistics, and the reconciliation that re-queues any narration or scoring request left without a result. The importer loads O*NET and ESCO and lists unresolved records (FR-31). Prototype: absent.

Data stores. The operational database is the system of record: relational tables for accounts, assignments, runs, events, evidence, reviews, ratings, and logs, and documents for content. The queue store holds jobs, rate limits, budget counters, and the publish--subscribe channel feeding event streams --- nothing that cannot be rebuilt from the database. The object store holds assets and exports. Prototype: the database, with 19 tables.

The assessed turn. A free-text answer in Perform scenario tests the architecture hardest, because it involves the explorer, the authority over scores, the models, and the failure of any of them. It has two phases: during the situation, the narrator answers the explorer (AI-4); when the situation ends, the judges score it in the background (AI-5). The figure below shows both as a sequence; the numbers in the steps refer to its messages.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.9\textheight,keepaspectratio]{figures/jobquest_seq_assessed_turn.png}
\caption{Sequence of one written answer: narration during the situation, background scoring when it ends, the time left to the models under NFR-01 and NFR-02, and the path taken when a provider fails}
\end{figure}

\begin{enumerate}[leftmargin=1.5em]
  \item Messages 1--4: the explorer application sends the answer with the run's next sequence number and an idempotency key, so a retry cannot record it twice (NFR-03, NFR-13). The API checks it with \textit{game-core}, stores it with a narration request in one transaction, enqueues the job directly after commit --- a transactional outbox\cite{r167} guarantees a job for every stored answer --- and replies that the answer is saved. Progress shows at once, and a status line after two seconds (NFR-01).
  \item Messages 5--10: a worker removes identifying details and sends the seed and the player's text to the narrator; the rubric and scoring keys are not in its prompt. The narration and any follow-up are shown only if they pass the rule checks --- numbers and names from the seed or the player's text, follow-ups within the count the engine allows --- and reach the explorer through Redis and the event stream (FR-12, NFR-15). A model of another family reviews the logs afterwards.
  \item Messages 11--13: when the situation ends, the API stores the event and a scoring request together and the job is queued. A worker sends the answers, as delimited data the models are instructed never to obey, to three judges of three families in parallel, at most three criteria per call. Each judge returns, per criterion, a verbatim quotation, a rationale, and a level; a judgment is kept only if the quotation occurs in what the player typed (FR-11, NFR-17). The median is the score, and judges more than one level apart flag the case for the expert (AI-3).
  \item Messages 14--17: the worker stores the results as events with their provenance; \textit{game-core} applies credit within the cap of BR-11; Redis carries the result to the API replica holding the explorer's stream, and result, feedback, and guidance appear as separate parts on the summary screen (FR-14, NFR-02, DR-07). Each event carries its sequence number, so a reconnecting stream replays whatever it missed from the database.
  \item Failure: the gateway retries, and may switch to another configured provider of an admissible family, which is still AI (DC-02). If a model stays unavailable, the session pauses with every answer and all progress saved, and the explorer is told within ten seconds (NFR-04); play resumes when the model returns, and pages that do not use AI, such as sign-in, the map, and the record, stay available. The scheduler re-queues any request left without a result, so not even loss of Redis loses an answer.
\end{enumerate}

A closed-format answer takes messages 1--4 only: the client shows \textit{game-core}'s score at once and the server recomputes it from the stored event. Resuming after an interruption (flow 7c) folds the stored events and returns the state at the last recorded position on any device.

Latency budget. Under the Lighthouse mobile profile\cite{r139}, the platform's own share of either phase is about 0.4 s: a 150 ms round trip to submit, 20 ms for the transaction, 10 ms to enqueue, 50 ms of preparation and checks, 20 ms to store the result, and half a round trip to push it. That leaves about 4.6 s of NFR-01's five seconds for the narrator to write a follow-up, and about 7.6 s of NFR-02's eight seconds for the judging panel, the budgets against which the first test of Section 5.2.3 measures candidate models; because the panel waits for all three judges, its time is that of the slowest. NFR-02 still states its bound per answer, while scoring now runs per situation in the background; the requirement is to be aligned with Section 5.2.3. Generated text is not streamed token by token, because it must pass the rule checks before display.

The in-flight figure follows from Little's law: 85 calls per second, each lasting three to eight seconds. Two sizing assumptions remain to be measured by the load tests of Chapter 7: if one single-vCPU API replica serves about 300 light requests per second, Stage 4 needs four replicas, six with headroom across two zones; if one worker holds 50 calls in flight, it needs six to fourteen workers.

The architecture scales for seven reasons. Processing tiers are stateless, so capacity grows by adding replicas. Fast and slow work are separated: a request stores and acknowledges in about 0.2 s, and slow work waits in a queue, so a class of forty starting together lengthens the queue rather than overloading the API. The binding constraint, the model tier, is isolated and limited on its own. Published content is immutable and therefore almost entirely served from cache. Reads for statistics are separated from writes by a replica. Load is shed by priority rather than by failure: under pressure, live narration goes first, background scoring waits a little longer for the summary screen, and authoring work waits for quiet hours. And no transaction spans services, so growth never requires distributed coordination. Canon content is approved once and served verbatim from releases, so run-time model calls are limited to narration, follow-ups, and scoring; the cost per playthrough is estimated in Section 5.2.3.

Reliability and operations. Availability of 99.5\% a month is proposed for Stages 1 and 2 and 99.9\% once two zones run (NFR-18). The write-ahead log is archived continuously and backups taken nightly, both copied to a second region in Vietnam, for a proposed recovery point of five minutes and recovery time of one hour. Deployments roll replica by replica behind health checks, with backward-compatible migrations so old and new versions run side by side. Monitoring tracks queue length, 95th-percentile latency per provider, cost per session, and error rates, alerting at the thresholds of NFR-01, NFR-02, and NFR-11. A web application firewall and TLS guard the entry, secrets are held in a secret manager, and the egress proxy admits only allowlisted model endpoints.

From the prototype to the target. Four prototype mechanisms are kept: rules in a framework-free \textit{game-core} shared by client and server; the server as score authority; content in versioned, immutable releases pinned to each run; and httpOnly cookie sessions with rotating refresh tokens. Six changes reach the target: free-text assessment becomes an asynchronous job whose result enters the run as an event; runs are submitted turn by turn (NFR-03); content is written through the lifecycle module instead of a seed script; three roles become four occupation-scoped actors; the staff application, AI orchestration, gateway, queue, workers, and scheduler are added; and the accessible 2D map is added. Each change extends a prototype component along a boundary it already has; none discards one.
