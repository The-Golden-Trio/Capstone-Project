\section{Implementation and Testing}

This chapter reports what has been built from the design of Chapter 5 and how it has been tested. Its reference date is 21 November 2026, on the working tree of the branch \texttt{feat/\allowbreak{}cham-\allowbreak{}ca-\allowbreak{}lam-\allowbreak{}checklist}. The prototype implements part of the requirements, so each statement says whether a part is \textit{implemented} (code runs and is tested), \textit{partly implemented}, or \textit{designed only}. Numbers of lines and tests were counted on that date by the commands listed in Appendix 6; they describe the size of the work and are not a measure of quality.

\subsection{Implementation}

\subsubsection{Approach}

The prototype was built to show that the technologies of Section 5.2 work for this system and to carry a vertical slice of the requirements: signing in, the catalogue, the staff authoring pipeline up to a draft game, and the explorer's play of a shift with AI narration and assessment. It was written before the design of Chapter 5 was complete, so some parts follow an earlier design and are listed as deviations in Section 6.1.5; the architecture itself is derived from the requirements, not from the prototype (Section 5.3.1), and the implementation is being moved toward it.

The database schema has 72 models and 11 migrations. Occupation data is kept as sources under \texttt{occupation-\allowbreak{}data/\allowbreak{}} and built into the JSON that \texttt{game-\allowbreak{}core} reads (\texttt{pnpm data:build}); generated files are never edited by hand. The local environment is one Docker Compose file with PostgreSQL, Redis, a mail catcher, and an S3-\allowbreak{}compatible store. Commits follow Conventional Commits and are checked by a hook and by the pull-\allowbreak{}request check.

A run of the activity flow against real models, done by hand on 11 November with the script \texttt{tools/\allowbreak{}dev/\allowbreak{}play-\allowbreak{}e2e.\allowbreak{}mjs}, gave the following observations: a follow-up question appeared after 1.8 to 5 seconds; the panel finished grading after 2.5 to 3.5 seconds; a level-one scenario cost about 0.0026 USD; reloading the page during a follow-up reopened the same place; and stopping the worker and starting it again let the pending job finish. These are single runs, not a benchmark; the measures and thresholds for NFR-01, NFR-02, and NFR-11 are fixed in Section 7.3.2 and have not yet been measured.

The one failure is a staff-\allowbreak{}application component test, \texttt{ReferenceAnswers.\allowbreak{}spec.\allowbreak{}tsx} (``keeps Không xét selected and does not turn a cleared score into zero''): the expected value \texttt{na} is read as an empty string. It is a defect of the working tree, to be fixed before the next release; it is reported here rather than hidden.

The tests concentrate where the design puts the risk. The shared rules have tests for the engines and for grading. The AI layer has tests of the gateway (adapters, circuit breaker, cost, model registry), of the provider contract, of the prompts, of the output parsers (including rejection of a quotation that is not in the answer), of the combination of judges, and of the checklist grading. The shift flow has a test of the whole flow through the queue with a fake model.

\subsubsection{How AI is tested without hiding failures}

There is no test path without AI (D-92). The fake model (\texttt{AI\_\allowbreak{}MODE=fake}) is used to check the flow only: queue, events, failover, and provenance; the log of the test run shows the expected ``no model'', ``too few judges'', and ``attempts exhausted'' paths being taken. It never stands in for a measurement of quality, which is made by the method of Section 7.3. Beyond unit tests there is an AI laboratory (\texttt{ai-\allowbreak{}lab}) that plays scripted playthroughs through the shift engine, the narrator, and the checker: one in which the player works well, one in which the player promises a time and forgets it, and one in which the player goes off topic, injects commands, and asks for the answer. It runs with fake models for free or with real models at a cost.

\subsubsection{Continuous integration and the plan of Section 5.3.9}

Each push to \texttt{main} and each pull request runs the format check, then lint, test, build, and typecheck on every project; a second check validates the commit messages and the description of the pull request. The CI environment holds placeholder database addresses and starts no database and no Redis, so no integration test runs in CI. There is no end-to-end test in the repository; the end-to-end run of Section 6.1.4 is a manual script.

The 187 test cases of Section 5.3.9 and Appendix 5 are a plan. The unit tests above were written before it and carry no case identifier, so this report does not claim that any of the 187 cases is covered, and it does not report code coverage, which has not been measured. Tagging the tests with case identifiers, adding PostgreSQL and Redis to CI, and choosing an end-to-end tool are tasks of the next phase.

\subsection{Summary}

The prototype implements the platform's backbone: identity and roles, the staff authoring pipeline to a draft game, the explorer's journey with the Galaxy Map, the shift play with AI narration, and AI assessment by a panel of judges, all through a queue, an event log, and a model gateway as designed. It does not yet implement reference-\allowbreak{}data import, the career and life modules, grading-\allowbreak{}quality tools, monitoring, release publication, and the migration to the new data model.
