## 1. Multi-provider integration: own SDK + adapter, client-side library, self-hosted proxy, hosted gateway / cloud catalogue

### Takeaway
All four approaches can reach the four model families JobQuest needs, but they differ in who sees the players' text: (a) and (b) send data only to the model providers; (c) adds a component the team operates; (d) adds a second foreign intermediary (a further recipient for the cross-border transfer dossier). No peer-reviewed study comparing these four approaches was found; documented numbers exist only for LiteLLM proxy overhead (vendor benchmark) and for OpenRouter/Vercel fees (official docs).

### Cited Findings

**(a) Each provider's own SDK behind a hand-written adapter**

- Structured output is a native feature at the providers checked: Anthropic documents "structured outputs" and tools with `strict: true`, where "the API compiles JSON schemas into grammars" — [Anthropic, API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) [official doc].
- Token usage is returned per call by the provider itself, e.g. Anthropic `usage.input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` — [Anthropic, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [official doc]; OpenAI `usage.input_tokens_details.cached_tokens` — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [official doc].
- Provider-specific parameters are only fully reachable through the provider's own API: Anthropic's `inference_geo` data-residency parameter "is also not available through the OpenAI SDK compatibility endpoint" — [Anthropic, Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency) [official doc].
- Data path: application to provider only; no intermediary. (Follows from the architecture; the provider data terms are in section 2.)

**(b) Client-side abstraction library (Vercel AI SDK, LangChain.js)**

- AI SDK: described as "the TypeScript toolkit designed to help developers build AI-powered applications and agents" — [AI SDK, Introduction](https://ai-sdk.dev/docs/introduction) [official doc]. The repository README says "The AI SDK provides a unified API to interact with model providers" and calls it a free, open-source library — [GitHub vercel/ai](https://github.com/vercel/ai) [official repository].
- AI SDK provider coverage: provider pages exist for OpenAI, Anthropic, Google, Google Vertex, Mistral, xAI Grok, Cohere, DeepSeek, Moonshot AI, Groq, Together AI, Fireworks, Alibaba, DeepInfra, Cerebras, Hugging Face, Baseten; the capability table has columns Image Input, Object Generation, Tool Usage, Tool Streaming, and the listed OpenAI, Anthropic, Google and Mistral models are all marked as supporting object generation — [AI SDK, Providers](https://ai-sdk.dev/providers/ai-sdk-providers) [official doc].
- AI SDK default routing caveat: "By default, the AI SDK uses the Vercel AI Gateway to give you access to all major providers out of the box"; passing a model string such as `'anthropic/...'` routes through the Gateway, and direct provider packages are the alternative — [GitHub vercel/ai](https://github.com/vercel/ai) [official repository].
- AI SDK telemetry: uses OpenTelemetry via `@ai-sdk/otel`; the recommended integration follows the GenAI semantic conventions and records `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.provider.name`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, and for streaming `gen_ai.client.operation.time_to_first_chunk`; `recordInputs` and `recordOutputs` default to true and can be set to false for sensitive inputs — [AI SDK, Telemetry](https://ai-sdk.dev/docs/ai-sdk-core/telemetry) [official doc].
- LangChain.js: "Each provider package implements the same standard interface, so you can swap providers without rewriting application logic"; integrations named include OpenAI, Anthropic, Azure OpenAI, Google Gemini, AWS Bedrock Converse, Ollama, OpenRouter and LiteLLM; `withStructuredOutput` accepts a zod schema and "the model output will also be validated against the schema using zod's parse methods"; `maxRetries` defaults to 6 with "exponential backoff with jitter"; the models page does not describe a model-fallback mechanism — [LangChain JS, Models](https://docs.langchain.com/oss/javascript/langchain/models) [official doc].
- Data path: the library runs inside the NestJS process; nothing passes through a third party unless the Gateway default (AI SDK) or a router integration is used.

**(c) Self-hosted proxy (LiteLLM)**

- LiteLLM is both a Python SDK ("a single, unified interface to call 100+ LLMs") and a proxy: "The proxy is a self-hosted OpenAI-compatible gateway"; features listed: spend tracking "per key, team, and user across all providers", "Built-in retry / fallback logic across multiple deployments", load balancing, virtual keys and budgets, guardrails including PII masking, logging callbacks to Langfuse, MLflow, Helicone; licence MIT per the footer link — [LiteLLM docs](https://docs.litellm.ai/docs/) [official doc].
- Latency overhead (vendor's own benchmark, fake OpenAI backend, Locust 1,000 users, machines with 4 CPU / 8 GB RAM, PostgreSQL, no Redis): with 4 instances the proxy overhead is median 2 ms, p95 8 ms, p99 13 ms at about 1,170 requests/s; with 2 instances median 12 ms, p95 29 ms, p99 43 ms. The page says results "should not be treated as universal production sizing guidance" — [LiteLLM, Benchmarks](https://docs.litellm.ai/docs/benchmarks) [vendor benchmark].
- Data path: prompts pass through a service the team hosts; if logging callbacks are enabled, they also go to the logging backend.

**(d) Hosted gateway or cloud model catalogue**

- OpenRouter fees: "OpenRouter charges a 5.5% ($0.80 minimum) fee when you purchase credits"; "We pass through the pricing of the underlying model providers without any markup"; with bring-your-own-key, usage above a monthly allowance "has a fee of 5% of what the same model and provider would normally cost on OpenRouter" — [OpenRouter FAQ](https://openrouter.ai/docs/faq) [official doc].
- OpenRouter failover and logging: "If a provider returns an error OpenRouter will automatically fall back to the next provider"; "We log basic request metadata (timestamps, model used, token counts)"; "Prompt and completion are not logged by default"; opting in to prompt logging gives a 1% discount — [OpenRouter FAQ](https://openrouter.ai/docs/faq) [official doc].
- OpenRouter data controls: "OpenRouter itself has a ZDR policy; your prompts are not retained unless you specifically opt in to prompt logging"; `provider.zdr: true` restricts routing to zero-data-retention endpoints; in-memory prompt caching is not counted as retention; "a provider's general policy may differ from the specific policy for a given endpoint" — [OpenRouter, ZDR](https://openrouter.ai/docs/guides/features/zdr) [official doc]. "Each provider on OpenRouter has its own data handling policies"; "If you opt out of training in your account settings, OpenRouter will not route to providers that train"; EU/US in-region routing exists on Business and Enterprise plans — [OpenRouter, Privacy and logging](https://openrouter.ai/docs/guides/privacy/logging) [official doc].
- OpenRouter structured output: "supports structured outputs for compatible models"; "Support is determined per endpoint, not just per model"; exact compliance with `strict: true` is not guaranteed on every endpoint; `require_parameters: true` restricts routing to endpoints that support the parameter — [OpenRouter, Structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) [official doc].
- Vercel AI Gateway: "AI Gateway routes requests across providers and fallback models, then records status, provider, latency, token usage, cost, and every routing attempt"; "AI Gateway adds zero markup to provider token prices, including with BYOK"; budgets per team, project, API key or member; callable from any infrastructure (page last updated 14 Sep 2026) — [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) [official doc].
- Vercel AI Gateway data handling: "AI Gateway uses zero data retention by default. It permanently deletes your prompts and responses after requests complete"; `zeroDataRetention: true` routes only to providers with verified ZDR agreements; a provider allowlist exists on Pro and Enterprise plans (page last updated 8 Sep 2026) — [Vercel AI Gateway, Security and compliance](https://vercel.com/docs/ai-gateway/security-and-compliance) [official doc].
- Amazon Bedrock: per-provider "Model Deployment Account" owned by the Bedrock service team; "Because the model providers don't have access to those accounts, they don't have access to Amazon Bedrock logs or to customer prompts and completions" — [Amazon Bedrock, Data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html) [official doc]. Retention is configured per Region with modes `none`, `default`, `aws_review`; with `none`, "No request or response data is written to durable storage by AWS or shared with the model provider"; some models (the page names Claude Fable 5 and Fable 5.1) require `aws_review`, under which prompts and completions "are retained within the AWS boundary for up to 30 days"; "Sharing content with model providers is not supported today" — [Amazon Bedrock, Data retention](https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html) [official doc].
- Google Vertex AI: partner and managed open models listed include Anthropic (Claude), xAI (Grok), Mistral AI, Meta (Llama), DeepSeek, Kimi, MiniMax, Qwen, GLM, and OpenAI open-weight models (`gpt-oss-120b`, `gpt-oss-20b`); proprietary OpenAI GPT models were not seen in the part of the page read — [Vertex AI, Use partner models](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-partner-models) [official doc]. "Google won't use your data to train or fine-tune any AI/ML models without your prior permission or instruction"; Gemini implicit caching is "stored only in-memory (not at-rest), is isolated at the project level, and has a 24-hour TTL" and can be disabled per project — [Vertex AI, Data governance](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance) [official doc].
- Microsoft Foundry ("models sold by Azure"): prompts and completions "are NOT available to other customers", "are NOT available to OpenAI or other providers of Models sold by Azure", and "are NOT used to train any generative AI foundation models without your permission or instruction"; prompts are processed within the customer-specified geography unless a Global or DataZone deployment is used, in which case they "may be processed in any geography where the relevant model sold by Azure is deployed" (page dated 18 May 2026) — [Microsoft Foundry, Data, privacy and security](https://learn.microsoft.com/en-us/azure/ai-foundry/responsible-ai/openai/data-privacy) [official doc]. The models-sold-by-Azure page (dated 21 Sep 2026) lists Azure OpenAI GPT models and mentions Cohere, DeepSeek, xAI Grok, Meta Llama and Mistral; Anthropic and Gemini do not appear on that page — [Microsoft Foundry, Models sold by Azure](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/models-sold-directly-by-azure) [official doc]. Separately, Anthropic's docs state that "Claude in Microsoft Foundry" exists and that there Anthropic is the data processor — [Anthropic, API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) [official doc].

**Evidence on lock-in and on abstraction not being enough**

- Ma, Yang and Kästner (arXiv 2311.11123, cs.SE, "conference version") report that LLM APIs are "updated silently and scheduled to be deprecated", that such changes can cause performance regressions and affect prompt design, and argue that regression testing must change because of prompt brittleness and non-determinism — [arXiv:2311.11123](https://arxiv.org/abs/2311.11123) [preprint of a conference paper; venue not named on the page].
- Provider-specific behaviour that an OpenAI-compatible layer does not carry: Anthropic's `inference_geo` is unavailable on its OpenAI-compatibility endpoint — [Anthropic, Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency) [official doc]; OpenRouter's structured-output enforcement "varies" by endpoint — [OpenRouter, Structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) [official doc].

### Inferences
- For DC-02 (replaceable provider) the decisive property is an internal interface owned by the team (for example `JudgeClient.score(answer, rubric) -> zod-validated object`); whether an SDK-per-provider adapter or the AI SDK sits behind it is a secondary choice. Both keep the data path at "application to provider", which keeps the list of foreign recipients for the transfer impact assessment as short as possible. (Interpretation.)
- A hosted gateway (OpenRouter, Vercel AI Gateway) gives failover, unified cost logs and one key, at the price of one more foreign organisation that receives the text in transit and whose routing can change which sub-provider serves a request. For a design that must name its recipients (Decree 356 Article 18 dossier content: recipient details, see section 3), endpoint-level routing would have to be pinned (provider allowlist / `provider.order` / ZDR flag). (Interpretation.)
- The AI SDK's default of routing string model IDs through the Vercel AI Gateway is a trap for this project: to keep data going only to the named providers, the code must use the direct provider packages explicitly. (Follows from the README statement.)
- DC-01 needs four model families. No single cloud catalogue page read today shows all of OpenAI proprietary + Anthropic + Google Gemini + Mistral in one place: Vertex lists Gemini, Claude, Mistral and only open-weight OpenAI; the Azure "sold by Azure" page lists OpenAI and Mistral but not Claude or Gemini. A single-cloud route would therefore constrain which four families can be chosen. (Based only on the pages read; the Bedrock catalogue could not be read, see Gaps.)
- LiteLLM's measured overhead (single-digit to low-tens of milliseconds at p95) is small relative to NFR-01/NFR-02 budgets of 5 s and 8 s; the cost of option (c) is operational (a Python service, a database, patching), not latency. (Inference from the vendor benchmark; not independently verified.)

### Gaps
- No peer-reviewed or reputable independent study comparing own-SDK adapters, client libraries, self-hosted proxies and hosted gateways was found; one targeted search returned only practitioner blogs and vendor content, which are not cited here.
- No documented latency overhead figure for OpenRouter or Vercel AI Gateway was found on the pages read (the OpenRouter FAQ gives none).
- The Amazon Bedrock model catalogue could not be read: the "supported models" page now only redirects to a "models at a glance" page that was not opened. Which provider families and which regions (including Singapore) Bedrock offers is therefore unverified.
- Licences not confirmed on the pages read: AI SDK (README says open-source, licence name not shown), LangChain.js, Presidio.
- Native structured-output documentation for OpenAI, Google and Mistral was not opened individually; support is evidenced only through the AI SDK capability table.

## 2. Provider data terms as of October 2026 (training use, retention, zero data retention, regions, age restrictions)

### Takeaway
For paid API use, OpenAI, Anthropic and Google state that inputs are not used for training by default; Mistral's position depends on plan (free mode may train; pay-as-you-go can opt out). None of the first-party APIs read offers regional processing in South-East Asia (OpenAI Singapore is storage-only and requires ZDR approval; Anthropic inference is "global" or "us"); Vertex AI has a Singapore region. The Gemini API terms forbid use in a service "directed towards or is likely to be accessed by individuals under the age of 18", and Anthropic requires extra safeguards for products that minors use — both matter if JobQuest admits school pupils.

### Cited Findings

**OpenAI (API)**

- Training: "data sent to the OpenAI API is not used to train or improve OpenAI models" by default, "unless you explicitly opt in to share data with us" — [OpenAI, Your data](https://developers.openai.com/api/docs/guides/your-data) [official doc].
- Retention: abuse-monitoring logs are "retained for up to 30 days" unless longer retention is legally required; application state varies by endpoint — same page.
- Zero Data Retention / Modified Abuse Monitoring: "Currently, these controls are subject to prior approval by OpenAI and acceptance of additional requirements"; `/v1/batches`, `/v1/files`, `/v1/evals`, `/v1/fine_tuning/jobs`, Assistants/threads, conversations and vector stores are marked not ZDR-eligible — same page.
- Regions: United States, Europe (EEA + Switzerland); Australia, Canada, Japan, India, South Korea, United Kingdom are regional storage only; UAE needs approval; Singapore (`sg.api.openai.com`) supports regional storage but not regional processing and requires ZDR or Modified Abuse Monitoring. "Data residency endpoints are charged a 10% uplift" for eligible models released on or after 5 March 2026 — same page.
- Prompt caching and data: "Caches are not shared across organizations and cannot be reused across regional processing boundaries"; caching "may store encrypted key/value tensors in GPU-local storage as application state" — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [official doc].
- Batch output files are "automatically ... deleted 30 days after the batch is complete" — [OpenAI, Batch](https://developers.openai.com/api/docs/guides/batch) [official doc].

**Anthropic (Claude API)**

- Training: "By default, we will not use your inputs or outputs from our commercial products" to train models; exceptions are explicit feedback/bug reports and opt-in (article dated 18 Aug 2026) — [Anthropic Privacy Center, Is my data used for model training?](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training) [official policy].
- Retention: "we automatically delete inputs and outputs on our backend within 30 days of receipt or generation"; inputs and outputs flagged for Usage Policy violations may be kept "for up to 2 years" (article dated 1 Jul 2026) — [Anthropic Privacy Center, How long do you store my organization's data?](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) [official policy].
- The developer documentation words the default differently: "Conversation content (your prompts and Claude's outputs) is not retained by default; the exception is Covered Models, which require 30-day retention", and "Retained data is never used for model training without your express permission" — [Anthropic, API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) [official doc]. The two official pages are not obviously consistent on the default (30 days vs not retained); record both and ask Anthropic or rely on the contract.
- ZDR: "Under a ZDR arrangement, Anthropic does not store customer prompts or responses at rest after the API response is returned"; requested through the sales team, enabled per organisation; Claude Fable 5/5.1 and Mythos 5/5.1 "require 30-day data retention and are not available under ZDR unless expressly authorized"; even with ZDR, flagged content may be retained "for up to 2 years" — same page.
- Regions: `inference_geo` accepts only `"global"` (default, "Inference may run in any available geography") and `"us"`; "Currently, `"us"` is the only available workspace geo"; US-only inference is priced at 1.1x on Claude 4.6 and later — [Anthropic, Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency) [official doc].
- Minors: "We define a minor or child to be any individual under the age of 18 years old, regardless of jurisdiction"; organisations giving minors direct access to products built on the API "must comply with the additional guidelines outlined in our Help Center article" (effective 15 Sep 2025) — [Anthropic, Usage Policy](https://www.anthropic.com/legal/aup) [official policy]. Those guidelines list "Age verification systems", "Content moderation and filtering", "Monitoring and reporting mechanisms", educational resources, compliance with applicable child-safety and data-privacy regulation stated on the organisation's website, and "Organizations must disclose to their users that they are interacting with an AI system rather than a human"; "Anthropic will periodically audit organizations for compliance" (dated 16 Mar 2026) — [Anthropic Help Center, organisations serving minors](https://support.claude.com/en/articles/9307344-responsible-use-of-anthropic-s-models-guidelines-for-organizations-serving-minors) [official policy].

**Google (Gemini API and Vertex AI)**

- Gemini API age terms: "You must be 18 years of age or older to use the APIs", and you will not use the Services as part of a website, application or other service that "is directed towards or is likely to be accessed by individuals under the age of 18" (terms effective 23 Mar 2026, page updated 28 Apr 2026) — [Gemini API Additional Terms of Service](https://ai.google.dev/gemini-api/terms) [official policy].
- Unpaid tier: "Google uses the content you submit to the Services and any generated responses to provide, improve," and develop products; "human reviewers may read, annotate, and process your API input and output"; "Do not submit sensitive, confidential, or personal information to the Unpaid Services" — same page. The pricing page confirms: Free plan content is "used to improve our products", Paid plan content is "not used to improve our products" (updated 7 Oct 2026) — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing) [official doc].
- Paid tier: "Google doesn't use your prompts ... or responses to improve our products"; "Google logs prompts and responses for a limited period of time" solely for detecting prohibited use; no number of days is given — [Gemini API Additional Terms of Service](https://ai.google.dev/gemini-api/terms) [official policy]; the ZDR page likewise gives no day count and says that a workload that "requires guaranteed zero data retention or enterprise data processing agreements" should use Vertex AI; Grounding with Google Search stores prompts and outputs for 30 days and cannot be disabled; implicit caching is RAM-only with a 24-hour TTL — [Gemini API, Zero data retention](https://ai.google.dev/gemini-api/docs/zdr) [official doc].
- Vertex AI regions: Asia-Pacific regions listed for generative AI are Mumbai, Singapore (`asia-southeast1`), Hong Kong, Taiwan, Tokyo, Sydney and Seoul; "Don't use the global endpoint if you have ML processing requirements" because "you can't control or know which region your ML processing requests are sent to"; "Endpoints don't guarantee data residency or in-region ML processing"; multi-region endpoints exist only for the US and EU — [Vertex AI, Locations](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/learn/locations) [official doc].
- Vertex AI ZDR path: abuse-monitoring logging applies to customers under the standard Google Cloud terms and an exception can be requested; request-response logging is off by default ("To achieve zero data retention, do not enable this feature") — [Vertex AI, Data governance](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance) [official doc].

**Mistral**

- Training by plan: Mistral Studio free mode — "we may use your data (input and output) to train our artificial intelligence models"; pay-as-you-go — "Customers retain full control over this processing and have the right to opt out at any time"; feedback ratings authorise use of the rated input and output on all plans — [Mistral Help Center, Do you use my user data to train your AI models?](https://help.mistral.ai/en/articles/347617-do-you-use-my-user-data-to-train-your-artificial-intelligence-models) [official policy].
- ZDR: "Zero data retention (ZDR) controls whether supported API inputs and outputs are retained after Mistral returns a response"; "ZDR is available on paid plans for supported stateless API calls"; requests are reviewed ("We review each request and may approve or deny it"); "ZDR and training opt-out are separate controls"; ZDR does not apply to Agents, batch processing files, Conversations, Libraries, `/v1/files`, or Labs models — [Mistral docs, Zero data retention](https://docs.mistral.ai/admin/monitor-comply/zero-data-retention) [official doc].

**Intermediaries**

- See section 1 for OpenRouter, Vercel AI Gateway, Bedrock, Vertex and Microsoft Foundry data terms.

### Inferences
- A free-tier Gemini key must not be used with player text or with Stage B real responses: the terms allow training and human review and tell users not to submit personal information. (Direct consequence of the terms.)
- If JobQuest is open to upper-secondary pupils (under 18), the Gemini API terms as read today appear to exclude Gemini via `ai.google.dev` for any player-facing call, and Anthropic's API becomes conditional on age verification, moderation, monitoring and AI disclosure. Whether Vertex AI's terms carry the same under-18 restriction was not checked. An 18+ gate (first-year students and above) would remove this constraint. (Interpretation; the product decision belongs to the team and the legal office.)
- No first-party API read offers processing confined to South-East Asia. In-region processing in Singapore is documented only for Vertex AI regional endpoints; that still is a transfer outside Vietnam under Law 91/2025 Article 20(1), so a Singapore region reduces distance, not the legal category. (Interpretation.)
- ZDR is by approval at OpenAI, Anthropic and Mistral, and is not available on batch endpoints at OpenAI and Mistral. A student project should plan for the default (up to 30 days of abuse-monitoring retention at the provider) and treat ZDR as a possible later improvement. Routing through a gateway with a ZDR flag (Vercel, OpenRouter) or Bedrock `data_retention_mode: none` is a self-service alternative, at the cost of adding an intermediary. (Interpretation.)

Third-party pages in search results mention a 30-day window; they were not opened and are not relied on.
- Google paid Gemini API: the abuse-monitoring retention period is "a limited period" with no number on the two pages read.

## 3. Vietnamese law: Law 91/2025/QH15 and Decree 356/2025/NĐ-CP

### Takeaway
Using a platform outside Vietnam to process personal data collected in Vietnam is expressly a cross-border transfer (Law Article 20(1)(c)) and requires a transfer impact assessment dossier sent to the specialised data-protection authority under the Ministry of Public Security within 60 days of the first transfer; none of the listed exemptions obviously fits a career game. De-identified data is outside the definition of personal data (Law Article 2(1)), but the Decree's sensitive-data list includes behaviour-tracking data from online services (Decree Article 4(1)(l)), which also switches off the small-enterprise and start-up relief. No exemption for research or educational institutions was found.

### Cited Findings

**Texts read and their status**

- Law 91/2025/QH15, Articles 1–39, full text on a third-party site; effective 1 January 2026 (Article 38) — [Luật Bảo vệ dữ liệu cá nhân 2025, ketoananpha.vn](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025) [legal text, unofficial reproduction].
- Decree 356/2025/NĐ-CP, Articles 1–42 (the annex forms were only partly read), effective 1 January 2026 and replacing Decree 13/2023/NĐ-CP (Article 42) — [Nghị định 356/2025/NĐ-CP, ketoananpha.vn](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp) [legal text, unofficial reproduction].
- EY Vietnam Legal Alert, March 2026, on Decree 356 (PDF, text extracted locally) — [EY Legal Alert](https://www.ey.com/content/dam/ey-unified-site/ey-com/en-vn/technical/tax/documents/ey-vietnam-legal-alert-march-2026-decree-no356-2025-nd-cp-providing-detailed-guidance-for-implementation-of-personal-data-protection-law-eng.pdf) [secondary summary].
- Not readable: `thuvienphapluat.vn` (403), PwC Vietnam PDF of 28 Jan 2026 (403). No official government-portal copy was found.

**(i) Cross-border transfer and the transfer impact assessment**

- Law Article 20(1) lists three cases of cross-border transfer: (a) moving personal data stored in Vietnam to a storage system outside Vietnam; (b) a Vietnamese agency, organisation or individual transferring personal data to a foreign organisation or individual; (c) "sử dụng nền tảng ở ngoài lãnh thổ nước Cộng hòa xã hội chủ nghĩa Việt Nam" "để xử lý dữ liệu cá nhân được thu thập tại Việt Nam" — [Law 91/2025, Art. 20](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Law Article 20(2): the transferring party "phải lập hồ sơ đánh giá tác động chuyển dữ liệu cá nhân xuyên biên giới" and "gửi 01 bản chính cho cơ quan chuyên trách bảo vệ dữ liệu cá nhân" "trong thời gian 60 ngày kể từ ngày đầu tiên chuyển dữ liệu cá nhân xuyên biên giới" — same source.
- Law Article 20(3)–(5): the assessment is done once for the entity's operating life and updated under Article 22; the authority inspects at most once a year unless there is a violation or incident; transfers may be stopped where they risk national defence or security — same source.
- Law Article 20(6), cases that do not require the assessment: (a) transfers by competent state agencies; (b) storing employees' personal data on cloud services; (c) a data subject transferring their own data across the border; (d) other cases set by the Government — same source.
- Decree Article 17(1) restates the three cases, including storage "trên dịch vụ điện toán đám mây của nhà cung cấp dịch vụ ở nước ngoài" (point a) and processing of data "được thu thập tại Việt Nam và chuyển đến nền tảng ở ngoài lãnh thổ nước Cộng hòa xã hội chủ nghĩa Việt Nam để tiếp tục xử lý" (point c) — [Decree 356/2025, Art. 17](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Decree Article 17(3), additional exemptions from the transfer impact assessment: (a) press and media activities; (b) data already made public under law; (c) emergencies to protect life, health and property; (d) cross-border personnel management under labour rules and collective agreements; (đ) providing data to conclude contracts or carry out procedures relating to cross-border transport, logistics, money transfer, payment, hotels, visa applications, scholarship applications — same source.
- Decree Article 18: the dossier contains the impact assessment report (Form 09), a copy of the transfer contract/agreement and the organisation's data-protection policies; the report covers recipient details, purposes, data types, consent, security measures and risk assessment (clauses 2–3). Clause 4: the dossier "phải luôn có sẵn" for inspection, and one original is filed online, in person or by post with the specialised authority "kèm theo Mẫu số 01a/01b" "trong thời hạn 60 ngày kể từ ngày tiến hành chuyển dữ liệu cá nhân xuyên biên giới". The authority answers within 15 days (clause 5); an incomplete dossier must be completed within 30 days (clause 6) — same source.
- Recipient authority: "Cơ quan chuyên trách bảo vệ dữ liệu cá nhân là đơn vị trực thuộc Bộ Công an" (Decree Article 39(1)) — same source. EY names it as the Department of Cybersecurity and High-Tech Crime Prevention — [EY Legal Alert](https://www.ey.com/content/dam/ey-unified-site/ey-com/en-vn/technical/tax/documents/ey-vietnam-legal-alert-march-2026-decree-no356-2025-nd-cp-providing-detailed-guidance-for-implementation-of-personal-data-protection-law-eng.pdf) [secondary summary].
- Updates: dossiers are updated every 6 months when there are changes, and within 10 days for certain changes such as reorganisation or dissolution (Decree Article 20; Law Article 22) — [Decree 356/2025, Art. 20](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Penalty: for an organisation violating the cross-border transfer rules the maximum fine is 5% of the previous year's revenue; the general maximum for other violations is VND 3 billion; individuals face half the organisational maximum (Law Article 8(4)–(6)) — [Law 91/2025, Art. 8](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Cloud contracts: contracts with cloud providers must cover compliance with Vietnamese law, data flows and roles, security measures, retention and deletion, and access control (Decree Article 12(2)); "Dữ liệu cá nhân trên điện toán đám mây phải được mã hóa ở trạng thái nghỉ và truyền" (Decree Article 12(4)) — [Decree 356/2025, Art. 12](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Controller–processor: a processor may receive personal data only after a contract or agreement with the controller and must process only as agreed; the controller remains liable to data subjects (Law Article 37) — [Law 91/2025, Art. 37](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Conflict between sources: EY describes Decree 356 as an "Ex-ante mechanism, requiring dossiers to be reviewed and approved" — [EY Legal Alert](https://www.ey.com/content/dam/ey-unified-site/ey-com/en-vn/technical/tax/documents/ey-vietnam-legal-alert-march-2026-decree-no356-2025-nd-cp-providing-detailed-guidance-for-implementation-of-personal-data-protection-law-eng.pdf); the Decree text as read sets filing within 60 days from the date the transfer is carried out, with a 15-day review — [Decree 356/2025, Art. 18](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp). Whether transfers may begin before the authority's "đạt" result is a question for the legal office.

**(ii) Children's data and consent**

- Law Article 24(2): for children and persons with limited or no civil capacity, "người đại diện theo pháp luật thay mặt thực hiện các quyền của chủ thể dữ liệu cá nhân", except in the cases of Article 19(1). For processing that publicises or discloses the private life or personal secrets of a child "từ đủ 07 tuổi trở lên", the consent of both the child and the legal representative is required — [Law 91/2025, Art. 24](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Law Article 24(3): processing must stop when the person who consented withdraws consent, or on request of a competent authority with sufficient grounds — same source.
- The Law's text as read does not define "trẻ em" and sets no age-verification duty in Article 24 — same source.
- Decree 356 contains no occurrence of "trẻ em" in Articles 1–42 as read — [Decree 356/2025](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Consent in general (Law Article 9): consent is "dựa trên sự tự nguyện và biết rõ các thông tin", must be "rõ ràng, cụ thể, có thể in, sao chép bằng văn bản", given "đối với từng mục đích", and "Sự im lặng hoặc không phản hồi không được coi là sự đồng ý" — [Law 91/2025, Art. 9](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025). Decree Article 6: verifiable forms of consent; the controller keeps consent records and bears the burden of proof; default or misleading consent settings are prohibited; data subjects must be told when the data is sensitive — [Decree 356/2025, Art. 6](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Processing without consent (Law Article 19(1)): urgent protection of life, health and rights; emergencies and security; state-agency operations; performance of the data subject's agreement with the relevant organisation as provided by law; other cases set by law — [Law 91/2025, Art. 19](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).

**(iii) Sensitive personal data and behavioural / online-activity data**

- The Law defines the two categories and delegates the lists to the Government (Law Article 2(2)–(3)) — [Law 91/2025, Art. 2](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Decree Article 4(1) lists sensitive data in points a–m: racial or ethnic origin; political, religious or belief views; private life, personal and family secrets; health status; biometric and genetic data; sex life or orientation; crime data held by enforcement bodies; location data from positioning services; e-ID credentials and ID-card images; bank account, card and financial transaction data; and, at point l: "Dữ liệu theo dõi hành vi, hoạt động sử dụng dịch vụ viễn thông, mạng xã hội, dịch vụ truyền thông trực tuyến và các dịch vụ khác trên không gian mạng"; point m is a catch-all for data that law requires to be kept secret — [Decree 356/2025, Art. 4](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- EY confirms the change: Decree 356 removes "data reflecting activities, activity history in cyberspace" from basic data and adds to sensitive data "behavior tracking data, usage data of telecommunications services, social networks, online media services, and other services in cyberspace" — [EY Legal Alert](https://www.ey.com/content/dam/ey-unified-site/ey-com/en-vn/technical/tax/documents/ey-vietnam-legal-alert-march-2026-decree-no356-2025-nd-cp-providing-detailed-guidance-for-implementation-of-personal-data-protection-law-eng.pdf) [secondary summary].
- Basic personal data (Decree Article 3) has 11 items, including names, date of birth, gender, addresses, nationality, image, phone / ID / passport / licence numbers, marital status, family relations, "Thông tin về tài khoản số của cá nhân", and other information that identifies a specific person and is not in Article 4 — [Decree 356/2025, Art. 3](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Controllers handling sensitive data must set access-restriction rules, processing procedures and security measures (Decree Article 4(2)); transfers of sensitive data require encryption, anonymisation or other security measures and physical security of devices (Decree Article 7(2)) — same source.

**(iv) Anonymised / de-identified data**

- Law Article 2(1): personal data is "dữ liệu số hoặc thông tin dưới dạng khác xác định hoặc giúp xác định một con người cụ thể", and "Dữ liệu cá nhân sau khi khử nhận dạng không còn là dữ liệu cá nhân" — [Law 91/2025, Art. 2](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Law Article 2(11): "Khử nhận dạng dữ liệu cá nhân là quá trình thay đổi hoặc xóa thông tin để tạo ra dữ liệu mới" that "không thể xác định hoặc không thể giúp xác định được một con người cụ thể" — same source.
- Law Article 14(6): whoever de-identifies data must control and supervise the process and prevent unauthorised access, copying, disclosure or loss; "Không được tái nhận dạng dữ liệu cá nhân sau khi đã được khử nhận dạng, trừ trường hợp pháp luật có quy định khác" — same source.
- Law Article 12(1): encrypted personal data "vẫn là dữ liệu cá nhân" — same source.
- Decree Article 9(3)(c) describes anonymisation ("ẩn danh") as "quá trình tách các dữ liệu xác định một con người cụ thể để lưu trữ và bảo mật riêng biệt"; the Ministry of Public Security with the Ministry of Science and Technology is to develop de-identification and anonymisation standards (Decree Articles 34(4), 36(1)) — [Decree 356/2025](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).

**(v) Exemptions: small enterprises, start-ups, research, education**

- Law Article 38(2): for 5 years from the Law's effective date, small enterprises and start-ups may choose whether to apply Article 21 (processing impact assessment), Article 22 (updating dossiers) and Article 33(2) (appointing data-protection staff or hiring a service provider), except those that provide personal-data processing services, directly process sensitive personal data, or process data of a large number of data subjects. Article 38(3): household businesses and micro-enterprises are not required to apply the same provisions, with the same exceptions — [Law 91/2025, Art. 38](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Decree Article 41(1)–(2) repeats this and fixes the threshold: the relief ends "kể từ thời điểm có quy mô đạt từ 100 nghìn chủ thể dữ liệu cá nhân trở lên dựa trên kết quả tích lũy tổng lượng dữ liệu cá nhân đã xử lý" — [Decree 356/2025, Art. 41](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- The provisions named in the relief are Articles 21, 22 and 33(2) of the Law. Article 20 (cross-border transfer) is not among them in either text as read — same two sources. EY's table nevertheless lists the scope of exemption as "Obligation to prepare, update, and submit DPIA, CTIA reports" — [EY Legal Alert](https://www.ey.com/content/dam/ey-unified-site/ey-com/en-vn/technical/tax/documents/ey-vietnam-legal-alert-march-2026-decree-no356-2025-nd-cp-providing-detailed-guidance-for-implementation-of-personal-data-protection-law-eng.pdf) [secondary summary]. The primary text and the secondary summary differ on whether the transfer assessment is covered.
- Neither text as read defines "doanh nghiệp nhỏ" or "doanh nghiệp khởi nghiệp" — same two primary sources.
- State agencies are exempt from the processing impact assessment of Article 21 — [Law 91/2025, Art. 21](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- No exemption for scientific research, statistics or educational institutions was found in the Law as read; scientific research appears only under international cooperation (Article 6(2)(d)) — [Law 91/2025](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).

**Other provisions that touch the design**

- Processing impact assessment: controllers and processors prepare and keep a dossier from the start of processing and file it within 60 days from the start of processing (Law Article 21; Decree Article 19) — [Decree 356/2025, Art. 19](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- AI: AI-based processing of personal data "must be classified by risk level" with matching protection (Law Article 30(4)) — [Law 91/2025, Art. 30](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025). Decree Article 10: personal data may be used to research and develop AI subject to the rules (clause 1); AI outputs that can identify a person must be protected (clause 2); the controller must notify the data subject of automated processing, explain how the algorithm works and its impact, and "đưa ra các lựa chọn để chủ thể dữ liệu có quyền không tham gia" (clause 3); compliance assessment once a year (clause 5(đ)); data subjects may edit, anonymise or delete identity records "kể cả khi nền tảng lưu trữ lịch sử hành vi" (clause 6) — [Decree 356/2025, Art. 10](https://ketoananpha.vn/nghi-dinh-356-2025-nd-cp).
- Online services (Law Article 29): no requirement of images or video of identity documents for account verification; an option to refuse cookies; a "không theo dõi" option or tracking only with consent — [Law 91/2025, Art. 29](https://ketoananpha.vn/luat-bao-ve-du-lieu-ca-nhan-nam-2025).
- Breach notification: "chậm nhất là 72 giờ kể từ khi phát hiện hành vi vi phạm" to the specialised authority in the serious cases listed (Law Article 23) — same source.
- Data-subject rights (Law Article 4(1)): to know, consent/refuse/withdraw, view and correct, request provision/deletion/restriction and object, complain and claim compensation, request protective measures — same source.

### Inferences
(All points in this list are interpretation, not legal advice.)

- Sending a player's answer from a server in Vietnam to a model API hosted abroad matches Law Article 20(1)(c) and Decree Article 17(1)(c) on their face, which confirms the team's DC-03 reading. None of the Article 20(6) or Decree Article 17(3) exemptions (state agency, employee data on cloud, data subject's own transfer, press, public data, emergency, HR management, transport/payment/visa/scholarship procedures) describes a career-exploration game.
- If answers are de-identified to the Law's standard before they leave the platform, what is sent is by definition not personal data (Article 2(1)), and Article 20 would not be engaged for that payload. The standard is strict ("không thể xác định hoặc không thể giúp xác định"), and section 4 shows that automatic redaction of free text does not reach 100% recall and that inference attacks survive redaction. A defensible position is therefore "redaction is a risk-reduction measure, and the transfer dossier is filed anyway", not "redaction makes the law inapplicable".
- A record of how a user plays (choices, answers, time on task, scores per competency) may fall under Decree Article 4(1)(l) "dữ liệu theo dõi hành vi, hoạt động sử dụng ... các dịch vụ khác trên không gian mạng". If so, JobQuest "directly processes sensitive personal data", the Article 38 / Article 41 relief is unavailable regardless of size, and Decree Article 6(4) (tell the data subject the data is sensitive) and Article 7(2) (encryption/anonymisation on transfer) apply. This is the single most consequential classification question.
- HCMUT is a public university, not obviously a "doanh nghiệp nhỏ / khởi nghiệp", "hộ kinh doanh" or a "cơ quan nhà nước" in the sense of the exemptions; a student capstone has no legal personality of its own. Who the controller is (the university, the faculty, the students as individuals) determines who files anything.
- Because the Law's Article 24 gives the legal representative the exercise of a child's rights and neither text read defines the age of a child, an 18+ only pilot is the simplest way to stay out of the children's-data question during Stage B; it also removes the provider-side under-18 restrictions in section 2.
- Decree Article 10(3) (notice of automated processing, explanation of the algorithm, and an option not to take part) maps directly onto AI-5 scoring: the product needs a plain-language notice that answers are scored by AI models, how, and an opt-out path.
- The dossier must name recipients and data types (Decree Article 18(3)); every additional intermediary (gateway, logging SaaS hosted abroad) is another recipient. This favours direct provider calls and self-hosted observability.

**Questions to put to the university's legal office**

1. Who is the personal data controller for JobQuest at each stage (Stage A synthetic only; Stage B with real players): the university, the faculty/lab, or the student team? Who signs and files a dossier?
2. Does a pilot run by a public university's student project fall within the Law at all in the same way as an enterprise, and is there any regime for research conducted by an educational institution that we have missed (none was found in the Law or Decree)?
3. Is game-play data (free-text answers, choices, competency scores, timestamps) "dữ liệu theo dõi hành vi, hoạt động sử dụng ... dịch vụ khác trên không gian mạng" under Decree 356 Article 4(1)(l), and therefore sensitive?
4. If answers are redacted of names, contacts and other identifiers before being sent to a foreign model API, does the university accept that the payload is "khử nhận dạng" under Law Article 2(11), or must we treat it as personal data and file a cross-border transfer impact assessment (Law Article 20; Decree Articles 17–18, Forms 09 and 01a/01b)?
5. May transfers start before the authority returns a result on the dossier (Decree Article 18(4)–(6) reads as filing within 60 days after the transfer starts; EY describes an ex-ante approval)?
6. Does the Article 38 / Decree Article 41 relief cover the cross-border transfer assessment (the text names Articles 21, 22 and 33(2) only; EY's summary says CTIA is included)?

8. Is a click-through data-processing addendum from a foreign model provider a sufficient "hợp đồng/thỏa thuận" for Decree Article 18(2) and Law Article 37, or is a signed contract needed?
9. What risk level does AI scoring of career-exploration answers fall into under Law Article 30(4), and what does the notice / explanation / opt-out of Decree Article 10(3) have to contain?
10. Are the experts' interview transcripts (AI-1) and the experts' identities personal data that also leave Vietnam, and do they need a separate consent and entry in the dossier?

## 4. De-identification of free text before it leaves the platform

### Takeaway
Automatic PII redaction is a useful risk reduction but is documented by its own maker as incomplete, and LLMs can still infer personal attributes from text that anonymisers have processed. Vietnamese resources exist for generic named entities (PhoBERT, PhoNLP, VnCoreNLP, underthesea) but no published precision/recall for PII detection in Vietnamese free text of this kind was found; the effect of redaction on rubric scoring of short answers is unmeasured and must be tested in Stage A.

### Cited Findings

**Tools**

- Microsoft Presidio (now maintained by "Data Privacy Stack"; "Presidio is transitioning to a community-owned project") provides an analyzer ("PII identification in text") and an anonymizer ("De-identify detected PII entities using different operators"), using "Named Entity Recognition, regular expressions, rule based logic and checksum" with context in multiple languages. Its own warning: "there is no guarantee that Presidio will find all sensitive information" and "additional systems and protections should be employed" — [Presidio documentation](https://presidio.dataprivacystack.org/) [official doc].
- LiteLLM's proxy lists PII masking among its guardrails — [LiteLLM docs](https://docs.litellm.ai/docs/) [official doc].

**Vietnamese NER resources**

- PhoBERT (Nguyen and Nguyen, Findings of EMNLP 2020): "improves the state-of-the-art in multiple Vietnamese-specific NLP tasks" including named-entity recognition, and consistently outperforms multilingual XLM-R; the abstract page gives no F1 number — [arXiv:2003.00744](https://arxiv.org/abs/2003.00744) [peer-reviewed, abstract page].
- PhoNLP (Nguyen and Nguyen, NAACL 2021 Demonstrations): joint model for Vietnamese POS tagging, NER and dependency parsing; claims state-of-the-art results and to outperform single-task PhoBERT fine-tuning; no numbers on the abstract page — [arXiv:2101.01476](https://arxiv.org/abs/2101.01476) [peer-reviewed, abstract page]. Input must be word-segmented ("each line represents a word-segmented sentence"), with VnCoreNLP recommended for segmentation; the repository shows a BSD-3-Clause licence while the arXiv abstract says Apache 2.0 — [GitHub VinAIResearch/PhoNLP](https://github.com/VinAIResearch/PhoNLP) [official repository].
- VnCoreNLP (Vu et al., NAACL 2018 Demonstrations): "a fast and accurate NLP annotation pipeline for Vietnamese" with word segmentation, POS tagging, NER and dependency parsing; Java 1.8+, with a Python wrapper `py_vncorenlp`; the README gives no accuracy figures — [GitHub vncorenlp/VnCoreNLP](https://github.com/vncorenlp/VnCoreNLP) [official repository].
- underthesea: Python toolkit with `ner(text)`, `word_tokenize`, `classify`, `sentiment`; Apache-2.0 as shown on the repository page; example entity labels LOC and PER; no NER accuracy reported on the page; no PII-detection function mentioned — [GitHub undertheseanlp/underthesea](https://github.com/undertheseanlp/underthesea) [official repository].
- PhoNER_COVID19 (Truong, Dao and Nguyen, NAACL 2021): first manually annotated COVID-19 NER dataset for Vietnamese; PhoBERT gives higher results than XLM-R; automatic Vietnamese word segmentation improves NER results — [arXiv:2104.03879](https://arxiv.org/abs/2104.03879) [peer-reviewed, abstract page].
- Multilingual PII detection: Rajgarhia et al. (2025) evaluate a hybrid of regular expressions and context-aware LLMs (RECAP) over "13 low-resource locales" and report that it outperforms fine-tuned NER models by 82% and zero-shot LLMs by 17% in weighted F1; the abstract does not name the locales or give absolute scores — [arXiv:2510.07551](https://arxiv.org/abs/2510.07551) [preprint].

**Residual re-identification risk**

- Pilán et al. (TAB, 2022): a corpus of 1,268 English court cases from the European Court of Human Rights annotated for which spans must be masked to conceal identity; the authors state that conventional de-identification is limited to detecting predefined semantic categories and propose metrics for both privacy protection and utility preservation — [arXiv:2202.00443](https://arxiv.org/abs/2202.00443) [preprint page; journal venue not shown on the page].
- Staab et al. (2023): on real Reddit profiles, LLMs infer personal attributes such as location, income and sex with up to 85% top-1 and 95% top-3 accuracy at about 100x lower cost and 240x less time than humans; the authors find that text anonymisation and model alignment are currently ineffective at protecting privacy against LLM inference (paraphrase of the abstract) — [arXiv:2310.07298](https://arxiv.org/abs/2310.07298) [preprint page; venue not shown].
- Staab et al. (ICLR, "Large Language Models are Advanced Anonymizers"): an LLM-based adversarial anonymisation framework evaluated with 13 LLMs "outperforms current commercial anonymizers" in both utility and privacy; a human study (n=50) preferred the LLM-anonymised texts — [arXiv:2402.13846](https://arxiv.org/abs/2402.13846) [peer-reviewed, abstract page].

**Effect of redaction on downstream tasks**

- Lothritz et al. (NoDaLiDa 2023, pp. 10–16): across nine downstream NLP tasks, six anonymisation strategies for personal names and two pre-trained models, "de-identification does have a negative impact on the performance of NLP models", but the drop is modest; pseudonymisation with random names generally performs best — [ACL Anthology 2023.nodalida-1.2](https://aclanthology.org/2023.nodalida-1.2/) [peer-reviewed].
- Pal et al. (Safe Generative AI Workshop, NeurIPS 2024): PII redaction changes sentiment-analysis and entailment performance by "typically around 1-5%", while comprehension question answering drops by more than 25% on redacted queries; the authors relate the loss to whether task-critical entities were removed — [arXiv:2411.05978](https://arxiv.org/abs/2411.05978) [workshop paper].

### Inferences
- JobQuest answers are responses to a fictional work scenario; the characters, company and numbers come from the seed, not from the player's life. Identifiers in the answer are therefore incidental (a player signing a name, mentioning a school or phone number), and the scoring rubric should not depend on them. On that reasoning, typed-placeholder or random-surrogate replacement of person names, phone numbers, e-mails, ID numbers and URLs is expected to cost little scoring accuracy (closer to the 1–5% class than the 25% class in Pal et al.). This is an expectation, not a measurement; the seed's own character names must be allow-listed so they are not redacted. (Interpretation.)
- The cheapest high-precision layer for Vietnamese is deterministic: regular expressions and checksums for phone numbers, e-mail, citizen ID numbers, bank accounts, URLs and student IDs, plus a NER model for person, location and organisation names. Presidio's architecture supports custom recognisers and NER back-ends, but it is Python, so in a NestJS back end it would be a sidecar service; a TypeScript regex layer plus a small Python NER service is an equivalent design. (Design inference.)
- Independently of redaction, the request should carry no account identifier: use a per-call random ID, strip user ID, e-mail and IP from the payload and from any telemetry (AI SDK `recordInputs: false` exists for this), and keep the mapping only in the Vietnamese database. That is pseudonymisation in addition to redaction. (Design inference.)
- Because LLMs can infer attributes from style and content (Staab et al.), redaction cannot be claimed to make answers anonymous in the strict sense of Law Article 2(11). The report should claim "identifiers removed, residual inference risk remains, measured recall X on our test set". (Interpretation.)
- Measurement that closes the gap: (1) build a Vietnamese/English test set of scenario answers seeded with synthetic identifiers, and report precision and recall per identifier type for the redaction pipeline; (2) in Stage A, score every benchmark answer twice, raw and redacted, and report the change in QWK and the share of answers whose panel median changes; (3) count false redactions of seed terms.

### Gaps
- No peer-reviewed precision/recall figures for PII detection in Vietnamese free text were found. Search results pointed to Meddies-PII and OpenMed Vietnamese PII models (clinical domain) and to PIIBench; none of these was opened, so they are leads only.
- NER F1 figures on VLSP 2016 for PhoBERT, PhoNLP, VnCoreNLP and underthesea are not on the pages read (abstract pages and READMEs); they are in the full papers, which were not opened. No figure is given here from memory.
- No independent precision/recall evaluation of Presidio was opened; the old FAQ URL returned 404.
- Presidio's out-of-the-box support for Vietnamese is not stated on the page read.
- No study measures the effect of redaction on rubric-based ordinal scoring of short answers by an LLM judge; the two studies cited are on classification, entailment, sentiment and question answering in English and other European languages.
- The full TAB and Staab papers were not read, so the detailed anonymiser comparison (which commercial tools, what residual accuracy after anonymisation) is not reported.

## 5. Cost control: prompt caching, batch APIs, routing and cascades, response caching, output limits, streaming

### Takeaway
Three documented price levers apply directly: cached input tokens (about 10% of the input price at Anthropic and Google, "up to 95%" discount at OpenAI), batch processing at 50% for anything that need not be real-time (Stage A benchmark, AI-3 offline checks), and limiting output tokens, which cost several times more than input tokens. Cascades and routers have published savings (up to 98% in FrugalGPT, "over 2 times" in RouteLLM) but on tasks unlike JobQuest's and they conflict with a fixed three-family judge panel.

### Cited Findings

**Prompt caching**

- Anthropic: "5-minute cache write tokens are 1.25 times the base input tokens price"; "1-hour cache write tokens are 2 times the base input tokens price"; "Cache read tokens are 0.1 times the base input tokens price", with exceptions (0.05x on Claude Opus 5.5 and Sonnet 5.5; 0.025x on Fable 5.1 and Mythos 5.1). "By default, the cache has a 5-minute lifetime. The cache is refreshed for no additional cost each time the cached content is used." Minimum cacheable prompt: 512 tokens for the current 5.5 models, 1,024 to 4,096 for older ones; "Shorter prompts cannot be cached ... and no error is returned". "Prompt caching has no effect on output token generation." — [Anthropic, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [official doc].
- OpenAI: "The minimum cacheable prompt length is 1,024 tokens for GPT-5.6 and later"; "Pay the model's reduced cached-input rate for reused tokens, discounted up to 95%"; cache entries on earlier models "typically remain active for around 5 to 10 minutes of inactivity, up to one hour"; on GPT-5.6 and later a cached prefix stays eligible at least 30 minutes; "Put stable developer instructions and shared reference material first"; the whole rendered prefix must match — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [official doc].
- Google: context caching is priced at 10% of the input rate for the models checked (Gemini 3.1 Flash-Lite $0.25 input, $0.025 cached; Gemini 3.1 Pro Preview $2.00 input, $0.20 cached, per 1M tokens), with storage billed per hour — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing) [official doc]. Implicit caching on Vertex is on by default with a 24-hour in-memory TTL — [Vertex AI, Data governance](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance) [official doc].

**Batch APIs**

- OpenAI Batch: "50% cost discount compared to synchronous APIs"; "Each batch completes within 24 hours (and often more quickly)"; batch rate limits are separate from per-model limits; endpoints include `/v1/responses` and `/v1/chat/completions` — [OpenAI, Batch](https://developers.openai.com/api/docs/guides/batch) [official doc].
- Anthropic Message Batches: "most batches finishing in less than 1 hour while reducing costs by 50%"; "All usage is charged at 50% of the standard API prices"; a batch is limited to 100,000 requests or 256 MB; batches expire if not complete within 24 hours; results are available for 29 days; "The pricing discounts from prompt caching and Message Batches can stack", with cache hits on a best-effort basis — [Anthropic, Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) [official doc].
- Google: Batch API gives a 50% cost reduction on the paid plan — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing) [official doc].
- Data caveat: OpenAI `/v1/batches` and `/v1/files` are not ZDR-eligible — [OpenAI, Your data](https://developers.openai.com/api/docs/guides/your-data) [official doc]; Mistral ZDR excludes batch processing files — [Mistral docs, Zero data retention](https://docs.mistral.ai/admin/monitor-comply/zero-data-retention) [official doc].

**Routing and cascades**

- FrugalGPT (Chen, Zaharia and Zou, 2023): names three strategies — prompt adaptation, LLM approximation, LLM cascade; reports that a learned cascade can match the best individual LLM (the example given is GPT-4) with up to 98% cost reduction, or improve accuracy over GPT-4 by 4% at the same cost (paraphrase of the abstract); notes API prices can differ by two orders of magnitude — [arXiv:2305.05176](https://arxiv.org/abs/2305.05176) [preprint].
- RouteLLM (Ong et al., 2024): routers trained on human preference data choose between a stronger and a weaker model and reduce costs "by over 2 times in certain cases" without compromising response quality on the benchmarks used; routers transfer when the model pair changes — [arXiv:2406.18665](https://arxiv.org/abs/2406.18665) [preprint].

**Response caching**

- GPTCache (Fu Bang, NLP-OSS 2023, pp. 212–218): a semantic cache that answers from stored responses; the only quantitative claim is that it can "increase response speed 2-10 times when the cache is hit"; no cost percentage is given — [ACL Anthology 2023.nlposs-1.24](https://aclanthology.org/2023.nlposs-1.24/) [peer-reviewed workshop paper].

**Output-length limits and price asymmetry**

- Output tokens cost several times more than input tokens on the price lists read: Claude Sonnet 5.5 $2 input / $10 output per MTok; Claude Haiku 5.5 "From $0.10 / input MTok, From $0.50 / output MTok"; Claude Opus 5.5 $4 / $20 — [Anthropic, Models overview](https://platform.claude.com/docs/en/about-claude/models/overview) [official doc]; Gemini 3.1 Flash-Lite $0.25 / $1.50 and Gemini 3.1 Pro Preview $2.00 / $12.00 (prompts up to 200k tokens), where output price is stated as "including thinking tokens" — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing) [official doc].
- Fees outside token prices: OpenRouter 5.5% on credit purchases — [OpenRouter FAQ](https://openrouter.ai/docs/faq) [official doc]; data-residency uplifts of 10% at OpenAI and 1.1x at Anthropic for US-only inference — [OpenAI, Your data](https://developers.openai.com/api/docs/guides/your-data), [Anthropic, Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency) [official docs].

**Budget enforcement**

- LiteLLM proxy tracks spend "per key, team, and user across all providers" and supports budgets — [LiteLLM docs](https://docs.litellm.ai/docs/) [official doc]; Vercel AI Gateway budgets per team, project, key or member reject new requests after the budget is exceeded, described as soft caps — [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) [official doc].

### Inferences

**A transparent method for cost per session (NFR-11).** For each model call, read the token counts from the provider's `usage` object and compute:

`cost_call = (T_in_uncached × P_in + T_cache_read × P_in × r + T_cache_write × P_in × w + T_out × P_out) / 1,000,000`

where `P_in`, `P_out` are list prices per million tokens for the pinned model on the access date, `r` is the cache-read multiplier (0.1, 0.05 or provider-specific) and `w` the cache-write multiplier (1.25 or 2 at Anthropic; providers with automatic caching have no write surcharge on the pages read). `T_out` must include reasoning/thinking tokens where the provider bills them as output. Then:

`cost_session = Σ over AI-4 narration calls + Σ over scored answers Σ over the 3 judges (cost_call) + follow-up question calls + retries and hedged duplicates`

and report the mean, the 95th percentile and the split by component, with the price table and its access date stored next to the result. Batch-eligible offline work is costed at 0.5 × the same formula.

- Illustration only (the token counts are assumptions, not measurements): one judge call on Claude Sonnet 5.5 with 2,000 tokens of rubric + seed context, 500 tokens of player answer and wrapper, and 400 output tokens costs (2,500 × $2 + 400 × $10) / 1e6 = $0.0090 uncached. With the 2,000-token prefix read from cache at 0.05x: (2,000 × $2 × 0.05 + 500 × $2 + 400 × $10) / 1e6 = $0.0052. After caching, the output tokens are about 77% of the call cost, so the output cap matters more than further prompt trimming. Prices from the Anthropic models overview page read on 8 Oct 2026.
- Caching fits the AI-5 design well: the decision "one call per judge scores all competencies" puts the rubric, anchors and scenario context in a stable prefix and the player's answer at the end, which is exactly the structure the OpenAI and Anthropic pages recommend. The prefix must exceed each provider's minimum (512 to 1,024 tokens on current models), and cache lifetimes of 5 to 30 minutes mean hits depend on traffic: with few concurrent players, many calls will miss. The hit rate must be measured, not assumed. (Inference.)
- Output order "verbatim quote, rationale, level" makes the rationale the main output cost. Capping rationale length per competency in the schema and prompt, and setting `max_tokens`, is the cheapest lever and also shortens latency (section 6). (Inference.)
- Batch pricing applies to Stage A benchmark runs, AI-3 offline review of playthroughs and offline model-based checking (D-89), none of which is real-time. It does not apply to run-time AI-4/AI-5. Batch endpoints are outside ZDR at OpenAI and Mistral, so batch should carry synthetic or redacted data only. (Inference.)
- A cheap-model-first cascade conflicts with DC-01 and the fixed three-family median panel: a router that sometimes skips or swaps a judge changes the measurement instrument that RP-2 validates. A cascade that is compatible with the design is "deterministic pre-checks first, panel second" (empty or off-topic answers never reach the panel), or "two judges first, third only on disagreement"; the latter changes the statistic and would have to be validated against the three-judge median in Stage A before use. (Interpretation.)
- Exact-match response caching is safe for deterministic content (canon text is already verbatim from the seed) and for identical retries (idempotency keys). Semantic caching of scores for "similar" answers is not appropriate for an assessment: two answers that are close in embedding space can differ in the one detail a rubric anchor depends on. (Interpretation.)
- Streaming does not reduce token cost; it only changes perceived waiting time (section 6). (Follows from pricing by tokens.)

### Gaps
- FrugalGPT and RouteLLM savings were measured on question-answering and chat benchmarks in English; no published evaluation of cascades for rubric-based ordinal scoring, or for Vietnamese, was found.
- No independent measurement of real-world prompt-cache hit rates for low-traffic applications was found; providers describe the mechanism, not hit rates.
- OpenAI and Mistral list prices were not read today, so a four-family price table cannot be completed from these notes; another researcher's model-selection notes should supply the pinned models and prices.
- Token counts per session for JobQuest do not exist yet (the prototype has no AI). The measurement that closes this: instrument the first end-to-end prototype, log `usage` per call, and compute the formula above over at least a few dozen full sessions per pilot role.
- Vietnamese text tokenises differently from English and differently per provider; no token-per-word figures for Vietnamese were collected.

## 6. Latency: parallel calls, hedged requests, streaming, asynchronous scoring

### Takeaway
The three judges should be called in parallel, which makes panel latency the slowest of the three and therefore sensitive to each provider's tail; the classical remedy is hedged requests (Dean and Barroso report a 99.9th-percentile drop from 1,800 ms to 74 ms for 2% extra requests in a Google benchmark), and OpenAI's own guidance is that output length dominates latency. No published latency measurements for multi-provider LLM judge panels were found; NFR-01 and NFR-02 need the project's own measurements.

### Cited Findings

- Fan-out makes tails dominate: if each server has a 1-in-100 chance of a slow (over one second) response and a request must collect responses from 100 such servers in parallel, "63% of user requests will take more than one second" — Dean and Barroso, "The Tail at Scale", Communications of the ACM 56(2), February 2013, pp. 74–80 — [author-hosted PDF](https://www.barroso.org/publications/TheTailAtScale.pdf) [peer-reviewed journal article]; bibliographic record at [Google Research](https://research.google/pubs/the-tail-at-scale/).
- Hedged requests, defined: issue the same request to multiple replicas and use whichever responds first; the client sends a secondary request after a brief delay and cancels outstanding requests once the first result arrives — same article.
- Measured benefit: "in a Google benchmark that reads the values for 1,000 keys stored in a BigTable table distributed across 100 different servers, sending a hedging request after a 10ms delay reduces the 99.9th-percentile latency for retrieving all 1,000 values from 1,800ms to 74ms while sending just 2% more requests" — same article.
- Bounding the extra load: deferring the hedge until the first request has been outstanding longer than the 95th-percentile expected latency "limits the additional load to approximately 5% while substantially shortening the latency tail" — same article.
- OpenAI's latency guidance lists seven principles: "Process tokens faster", "Generate fewer tokens", "Use fewer input tokens", "Make fewer requests", "Parallelize", "Make your users wait less", "Don't default to an LLM". Quantitative heuristics: "cutting 50% of your output tokens may cut ~50% of your latency", whereas "cutting 50% of your prompt may only result in a 1–5% latency improvement"; streaming is "The single most effective approach, as it cuts the waiting time to a second or less" — [OpenAI, Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization) [official doc].
- Prompt caching and latency: Anthropic says "You will generally see improved time-to-first-token for long documents" and that caching "has no effect on output token generation" — [Anthropic, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [official doc]; OpenAI says caching reduces "the time spent processing input before the response starts" and gives no percentage — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [official doc].
- Relative model latency is published only qualitatively by Anthropic (Haiku 5.5 "Fastest", Sonnet 5.5 "Fast", Opus 5.5 "Moderate"), with the note that "Actual latency depends on prompt length, output length, and thinking effort" — [Anthropic, Models overview](https://platform.claude.com/docs/en/about-claude/models/overview) [official doc].
- Gateway-level failover exists as a product feature: OpenRouter "will automatically fall back to the next provider" on error — [OpenRouter FAQ](https://openrouter.ai/docs/faq) [official doc]; Vercel AI Gateway supports ordered provider and model fallbacks — [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) [official doc]; LiteLLM Router has "Built-in retry / fallback logic across multiple deployments" — [LiteLLM docs](https://docs.litellm.ai/docs/) [official doc]. LangChain.js retries up to 6 times by default with exponential backoff — [LangChain JS, Models](https://docs.langchain.com/oss/javascript/langchain/models) [official doc].
- Batch processing is the asynchronous extreme: results within 24 hours at OpenAI, most within 1 hour at Anthropic — [OpenAI, Batch](https://developers.openai.com/api/docs/guides/batch), [Anthropic, Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) [official docs].

### Inferences
- With three judges called in parallel and assumed independent, the panel finishes within a deadline only if all three do. If each judge individually meets the deadline 95% of the time, the panel meets it 0.95³ ≈ 85.7% of the time; for the panel to meet NFR-02 (8 s) at p95, each judge must meet it about 98.3% of the time (0.95^(1/3)). This is arithmetic under an independence assumption, the same reasoning as the fan-out example in Dean and Barroso; provider incidents are not independent of load, so real behaviour must be measured.
- Two design responses follow. (1) Deadline with degradation: return the median of the judges that answered by the deadline (two of three), mark the score provisional, and reconcile when the third arrives; this must be validated because a two-judge "median" is a different statistic. (2) Hedging within a family: after the per-family p95 has elapsed, send a second request to the same model (or the same family through a second host, such as a cloud catalogue) and take the first valid response; by Dean and Barroso's reasoning this adds roughly 5% more calls, hence roughly 5% more token cost. Hedging to a different family would break DC-01 unless that family is not otherwise on the panel. (Interpretation.)
- A structured judge output (quote, rationale, level for every competency) cannot be shown meaningfully while streaming, and the schema is validated only when complete. For AI-5, streaming helps perceived latency only if the UI shows progress or the narration (AI-4) continues while scoring completes. For AI-4 narration, streaming text into the visual-novel dialogue box is the natural fit and is the lever OpenAI calls most effective. (Interpretation.)
- Asynchronous scoring is compatible with the game design: the engine, not the model, controls the order of activities, so the next canon event can be displayed from the seed while the panel runs, with scores and feedback delivered at a checkpoint. Follow-up questions that depend on the score are the exception and need the synchronous path. NFR-04 (no committed progress lost on provider failure) follows from persisting the answer and enqueuing the scoring job before any provider call. (Design inference.)
- Because latency scales with output tokens far more than with input tokens, the rationale-length cap is also the main latency lever for AI-5; reasoning effort settings on newer models add hidden output tokens and should be pinned and logged. (Inference from the OpenAI heuristics and the Gemini note that thinking tokens are billed as output.)

### Gaps
- No published measurement of latency for parallel multi-provider LLM calls or for hedged LLM requests was found; the hedging figures are from a 2013 storage-system benchmark and transfer only as a principle.
- No time-to-first-token or tokens-per-second figures for specific models were collected; providers' pages read today give only qualitative ranks. Independent trackers were not consulted.
- Network latency from Vietnam to each provider's endpoints (US, EU, Singapore) was not measured and no source for it was found.
- The measurement that closes this: a load test from the deployment region that records, per judge family, the distribution of total latency for a realistic rubric prompt, then computes the panel's p95 under "all three" and "two of three" rules.

## 7. Observability: what to log per model call for audit and reproducibility

### Takeaway
Log, for every call, the exact model identifier returned by the provider, the prompt and rubric version, sampling parameters, token counts including cached tokens, computed cost with the price-table date, latency, finish reason, provider request ID and the validated output — because published studies show that the same API model name can change behaviour within months and that "deterministic" settings are not repeatable. Message content should be opt-in in telemetry and kept in the project's own database in Vietnam.

### Cited Findings

- Drift: Chen, Zaharia and Zou (2023) compared March and June 2023 versions of GPT-3.5 and GPT-4; GPT-4's accuracy on identifying prime vs composite numbers fell from 84% to 51%; both models made more formatting mistakes in code generation in June; the authors conclude the behaviour of the "same" LLM service can change substantially in a short time, highlighting "the need for continuous monitoring of LLMs" — [arXiv:2307.09009](https://arxiv.org/abs/2307.09009) [preprint].
- Non-determinism: Atil et al. (2024) ran five LLMs configured to be deterministic on eight tasks across 10 runs; accuracy varied by up to 15% across runs, the gap between best and worst possible performance reached up to 70%, and no LLM consistently delivered repeatable accuracy or identical output strings; they introduce TARr@N and TARa@N (total agreement rate over raw outputs and over parsed answers) — [arXiv:2408.04667](https://arxiv.org/abs/2408.04667) [preprint].
- API evolution: Ma, Yang and Kästner argue that LLM APIs are "updated silently and scheduled to be deprecated", that prompts are brittle under such changes, and that regression testing must be rethought for LLM APIs — [arXiv:2311.11123](https://arxiv.org/abs/2311.11123) [preprint of a conference paper].
- Reproducible evaluation: Biderman et al. (2024) identify sensitivity of models to evaluation setup, difficulty of comparison across methods, and lack of reproducibility and transparency, and "make recommendations to the field for improving evaluation rigor and confidence" — [arXiv:2405.14782](https://arxiv.org/abs/2405.14782) [preprint].
- Version pinning at Anthropic: "Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on"; retirement dates are published per model (for example Claude Sonnet 5.5 "Not sooner than September 28, 2027") — [Anthropic, Models overview](https://platform.claude.com/docs/en/about-claude/models/overview) [official doc].
- Deprecation notice at OpenAI: "We provide advance notice before retiring models"; at least 6 months for generally available models, at least 3 months for specialised variants, and preview models may be retired on much shorter notice "such as 2 weeks"; example entry: on 11 June 2026 developers using older GPT-5 and o3 snapshots were notified of removal on 11 December 2026; aliases map to snapshots (for example `gpt-3.5-turbo-0125` | `gpt-3.5-turbo`) — [OpenAI, Deprecations](https://developers.openai.com/api/docs/deprecations) [official doc].
- Telemetry standard: the OpenTelemetry GenAI semantic conventions now live in their own repository, covering "spans, metrics, and events for GenAI clients" (Apache-2.0) — [GitHub open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) [official repository]; the spans document is marked Status: Development and states "Model instructions, user messages, and model outputs are considered sensitive and are often large in size"; instrumentations should not capture them by default but offer opt-in, recording to `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages` or storing content externally with a reference — [GenAI spans (raw)](https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-spans.md) [official specification, development status].
- Attribute names in practice: the AI SDK's OpenTelemetry integration records `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.provider.name`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons` and `gen_ai.client.operation.time_to_first_chunk` — [AI SDK, Telemetry](https://ai-sdk.dev/docs/ai-sdk-core/telemetry) [official doc].
- Token fields for cost audit: Anthropic `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens` — [Anthropic, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [official doc]; OpenAI `usage.input_tokens_details.cached_tokens` — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [official doc]; Anthropic also returns `usage.inference_geo`, "indicating where inference ran" — [Anthropic, Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency) [official doc].
- Gateway logs: Vercel AI Gateway "records status, provider, latency, token usage, cost, and every routing attempt" — [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) [official doc]; OpenRouter logs "basic request metadata (timestamps, model used, token counts)" by default — [OpenRouter FAQ](https://openrouter.ai/docs/faq) [official doc].

### Inferences
A per-call log record that would let an auditor reproduce or explain any score (design proposal derived from the findings above):

- Identity and linkage: call ID; session ID and answer ID as internal pseudonymous keys (no account identifiers); component (AI-1 to AI-5); judge slot; attempt number and whether the call was a retry or a hedge.
- Model: provider; requested model ID; model ID returned in the response (the two can differ when an alias is used); endpoint or region, and the provider's reported inference location where available; SDK and adapter version.
- Prompt: prompt-template version (hash), rubric/seed version (hash), output schema version; whether redaction was applied and the redactor version.
- Parameters: temperature, top-p, max output tokens, reasoning/effort setting, seed if the provider supports one, structured-output mode.
- Usage and cost: uncached input tokens, cache-read tokens, cache-write tokens, output tokens (including reasoning tokens), computed cost, and the date of the price table used.
- Timing: request start, time to first token where streamed, total latency, provider request ID.
- Outcome: finish reason, schema-validation result, parsed output (quote, rationale, level per competency), refusal or error class, panel median and disagreement flag at the answer level.

- Content handling: store the redacted prompt and the raw response in the project's PostgreSQL in Vietnam, under access control and a retention period, and keep external telemetry content-free (`recordInputs: false`, `recordOutputs: false`), in line with the OpenTelemetry guidance that content capture be opt-in. A hosted observability SaaS abroad that receives prompt content would be another cross-border recipient under section 3. (Interpretation.)
- Version drift control: pin snapshot model IDs, never floating aliases, for the three judges; record the returned model ID on every call; keep a frozen regression set from the Stage A benchmark and re-run it on a schedule and whenever a provider announces a deprecation; treat any change of judge model as a new instrument that needs re-validation against NFR-14 before it replaces the old one. OpenAI's 6-month and Anthropic's published retirement dates give the planning horizon. (Inference from Chen et al., Ma et al. and the deprecation pages.)
- Repeatability reporting: because deterministic settings do not guarantee identical outputs (Atil et al.), the Stage A report should give score stability across repeated runs of the same answers (for example the share of answers whose panel median is identical over N runs) alongside QWK, rather than assuming a seed makes results reproducible. (Inference.)
